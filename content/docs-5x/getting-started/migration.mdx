---
title: "Upgrade to 5.x"
description: "Plan the license, schema, runtime identity, and application changes before rollout."
---

Treat the commercial 5.x line as an application upgrade. Updating a package reference alone does not migrate an existing operational store.

## Prepare the rollout

1. Confirm the [license entitlement and certificate](/docs/5.x/getting-started/licensing) for your deployment.
2. Align all TickerQ packages to one matching full version for your .NET target.
3. Back up the operational store and persistent Data Protection key ring, and verify your rollback procedure.
4. Review the new [application namespace and automatic reconciliation epoch](/docs/5.x/guides/configuration).
5. Generate and inspect application-owned EF migrations, or review your MongoDB/Redis upgrade requirements.
6. Drain writers that predate the runtime partition/activation protocol before the first adoption. New fencing cannot control old binaries that do not participate in it.
7. Validate the upgrade against a representative copy of your data before production.

## Review these API changes

| Area | What to check |
| --- | --- |
| Runtime identity | Use `UseApplicationNamespace(...)`. Do not generate a namespace per process. TickerQ manages the reconciliation epoch; `UseReconciliationEpoch(...)` is only for [manual control](/docs/5.x/guides/configuration#manual-epochs). |
| Code-defined crons | `[TickerFunction("Name", "<cron>")]` and `WithCron(...)` no longer declare schedules; a cron argument is a compile error. Move each schedule to `options.SeedCronTickers(crons => crons.Add("Name", "<cron>"))`. The key defaults to the function name, so existing rows are kept. See [moving from attribute schedules](/docs/5.x/guides/scheduling/cron-ticker#moving-from-attribute-schedules). |
| Cron overlap | Set `CronTickerEntity.SkipIfAlreadyRunning`; remove calls to the old function-context helper. |
| Transactional scheduling | Use `StageAsync` on a scoped EF application context when jobs must commit with business data. `AddAsync` still persists independently. |
| Chains | Add schema for recurring chains and deletion behavior; preserve existing graph ownership when migrating. |
| Progress and in-place retry | Add progress columns on time/cron executions and chain retry checkpoint columns on time jobs. |
| Dashboard | Configure authentication explicitly. Review signing keys, proxy trust, and cross-origin settings. |
| Nodes | Add `TickerQNodes` and `TickerQControlCommands` before using node discovery or cross-node cancellation. |
| Saved work | Add `TickerQDefinitions` before saving drafts or chain templates. |
| AI history | The EF model includes conversation, message, investigation, lease, and budget tables. `AddAssistantHistory()` enables their runtime services; apply the schema before assistant history or automatic investigation. |
| EF Core dependencies | `TickerQ.EntityFrameworkCore` no longer depends on `FlexLabs.EntityFrameworkCore.Upsert`. If your application calls `Upsert(...)` itself, add a direct package reference. |
| Function registry | `TickerFunctionProvider.TickerFunctions`, `TickerFunctionRequestTypes`, and `TickerFunctionRequestInfos` are read-only properties. Read them as before; register functions with `[TickerFunction]` or `MapTicker` instead of assigning them. Recompile code that reads them. |
| Integrations | The package and API names are `TickerQ.Integrations`, `AddIntegrations`, and `IntegrationSettings`. Rename existing preview storage without dropping encrypted settings. |
| Execution logs | The EF model includes `ExecutionLogs`; apply the current schema before enabling database log storage. |
| Schedule policies | The EF model always includes `SchedulePolicies` and the policy and late-start columns on `TimeTickers` and `CronTickers`, even when no policy is configured. Add them with an application-owned migration before the new binary starts. MongoDB creates its index at startup; Redis needs no schema step. See [schedule policy storage](/docs/5.x/guides/storage-upgrade#add-schedule-policy-storage). |
| Late starts | `SkipStaleCronOccurrencesOnStartup(...)` and `StaleCronOccurrenceThreshold` were removed. Set `WhenMissed(MissedExecutionPolicy.SkipAfter(...))` on each schedule that must not run late, and `CatchUp(CronCatchUpMode.RunLatest)` where a cron should run its latest slot missed during downtime. See [removed stale-occurrence options](/docs/5.x/guides/storage-upgrade#removed-stale-occurrence-options) and [late starts and catch-up](/docs/5.x/guides/schedule-policies/late-starts). |

## Storage is application-owned

Do not copy another application's migration history into your database, run `EnsureCreated` as an upgrade, or mark all legacy rows as belonging to one app without verifying their owner.

The [storage upgrade reference](/docs/5.x/guides/storage-upgrade) covers required columns, indexes, legacy ownership mapping, interrupted activation, and rollback limits for each provider. Follow it before starting the new scheduler against existing data.

After deployment, check activation and license status, verify a one-time and recurring execution, inspect chain progress, and confirm monitoring and integrations can read their retained state.
