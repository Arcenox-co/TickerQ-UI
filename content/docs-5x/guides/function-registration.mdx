---
title: "Function registration"
description: "Choose typed classes, attributes, or delegates, and keep scheduled function identities stable."
---

TickerQ supports three registration styles. Use the one that fits your application; all three register functions for the same time and cron managers.

| Style | Best fit | Registration |
| --- | --- | --- |
| `ITickerFunction` | One class per job with explicit DI registration | `builder.Services.MapTicker<TFunction>()` |
| `[TickerFunction]` | Job methods with generated dispatch and request/result metadata | Annotate a method; the source generator discovers it |
| Delegate | A small handler registered during startup | `builder.Services.MapTicker("Name", handler)` |

Register functions before `builder.Build()` and `app.UseTickerQ()`. These examples extend the [quick start](/docs/5.x/getting-started/quick-start); keep its TickerQ registration and runtime identity.

## ITickerFunction (default)

```csharp
using TickerQ.DependencyInjection;
using TickerQ.Utilities.Base;
using TickerQ.Utilities.Interfaces;

builder.Services.MapTicker<CleanupJob>()
    .WithMaxConcurrency(1);

public class CleanupJob(ILogger<CleanupJob> logger) : ITickerFunction
{
    public Task ExecuteAsync(TickerFunctionContext context, CancellationToken cancellationToken)
    {
        cancellationToken.ThrowIfCancellationRequested();
        logger.LogInformation("Cleanup job {JobId}", context.Id);
        return Task.CompletedTask;
    }
}
```

The default function name is the class name, `CleanupJob`. Its DI lifetime is scoped unless you supply another lifetime, such as `MapTicker<CleanupJob>(ServiceLifetime.Singleton)`. If the class is already registered in DI, that existing registration is kept. The instance is resolved from each attempt's scope, so a singleton function must not depend on scoped services. Renaming the class changes the default persisted function identity; plan that change for existing jobs.

Schedule it through a scoped manager:

```csharp
var result = await timeTickerManager.AddAsync<CleanupJob>(
    DateTime.UtcNow.AddMinutes(5), cancellationToken);
if (!result.IsSucceeded)
    throw result.Exception;
```

For a typed request, implement `ITickerFunction<TRequest>`, register with `MapTicker<TFunction, TRequest>()`, then call `AddAsync<TFunction, TRequest>(executionTime, request, cancellationToken)`. Cron managers have the equivalent overload with a cron expression instead of an execution time. The typed `TimeSchedule` and `CronSchedule` overloads add a business calendar, a late-start rule, and, for cron, a per-schedule time zone; see [time tickers](/docs/5.x/guides/scheduling/time-ticker#business-calendars-and-late-starts) and [cron tickers](/docs/5.x/guides/scheduling/cron-ticker#time-zones-calendars-and-catch-up). Use entity-based creation when setting retries, timeouts, overlap, or chain templates.

## [TickerFunction] attribute

Use an annotated method when you prefer to keep several functions in one class or want the generator to declare request and result metadata from the method signature and attribute:

```csharp
using TickerQ.Utilities.Base;

public class MaintenanceJobs(ILogger<MaintenanceJobs> logger)
{
    [TickerFunction("Maintenance.Cleanup", maxConcurrency: 1)]
    public Task CleanupAsync(
        TickerFunctionContext context,
        CancellationToken cancellationToken)
    {
        cancellationToken.ThrowIfCancellationRequested();
        logger.LogInformation("Cleanup job {JobId}", context.Id);
        return Task.CompletedTask;
    }
}
```

The source generator registers `Maintenance.Cleanup`; do not also call `MapTicker` for that same function. Use an explicit, stable attribute name because persisted jobs and schedules refer to it.

Generated code creates the class through its constructor and resolves each parameter from DI. When the class has several constructors, mark the one to use with `[TickerQConstructor]` from `TickerQ.Utilities.Base`. Without it, the generator uses the primary constructor, or else the first public constructor in source order.

```csharp
using TickerQ.Utilities.Base;

public class ReportJobs
{
    private readonly ILogger<ReportJobs> _logger;

    public ReportJobs() : this(Microsoft.Extensions.Logging.Abstractions.NullLogger<ReportJobs>.Instance) { }

    [TickerQConstructor]
    public ReportJobs(ILogger<ReportJobs> logger) => _logger = logger;

    [TickerFunction("Reports.Refresh")]
    public Task RefreshAsync(TickerFunctionContext context, CancellationToken cancellationToken)
    {
        _logger.LogInformation("Refresh reports for job {JobId}", context.Id);
        return Task.CompletedTask;
    }
}
```

The generated registration code in each assembly runs from a module initializer. .NET runs it the first time code touches a type from that assembly; loading the assembly alone does not run it. When attribute functions live in an assembly the host never references directly, such as a plug-in or feature library, `AddTickerQDiscovery` runs that registration explicitly. It is safe to list an assembly more than once:

```csharp
using System.Reflection;
using TickerQ.DependencyInjection;

builder.Services.AddTickerQ(options =>
{
    // Keep your existing namespace, epoch, and storage configuration.
    options.AddTickerQDiscovery([Assembly.Load("Contoso.Maintenance.Jobs")]);
});
```

Confirm the expected names in **About → Functions** after startup.

## Return output from a job class

A class implementing `ITickerFunction` can publish output for a child even though `ExecuteAsync` returns `Task`. Call `context.SetResult(value, jsonTypeInfo)` inside the parent and `context.GetParentResult(jsonTypeInfo)` inside an `OnSuccess` child. `ITickerFunction<TRequest>` supports the same pattern; `TRequest` remains the input type.

Follow the [CleanupJob → CleanupSummaryJob example](/docs/5.x/guides/requests-results#publish-from-an-itickerfunction-class) for the result DTO, both handlers, generated JSON metadata, registration, and chain scheduling. Attribute-based `ResultType` is a different registration path; do not add `[TickerFunction]` to a method already registered through `MapTicker`.

## Register a recurring function

Registering a function does not schedule it. Declare its recurring schedule with `SeedCronTickers`:

```csharp
builder.Services.AddTickerQ(options =>
{
    // Keep your existing namespace, epoch, and storage configuration.
    options.SeedCronTickers(crons => crons.Add("CleanupJob", "0 2 * * *"));
});

builder.Services.MapTicker<CleanupJob>()
    .WithMaxConcurrency(1);
```

The seeded schedule is created once during startup reconciliation and never duplicated by restarts
or replicas. This shorthand uses the [scheduler time zone](/docs/5.x/guides/scheduler#time-zones),
not the browser's display zone. When a schedule needs its own zone, a schedule policy, a request
payload, or chain steps, seed it with the [chain builder](/docs/5.x/guides/scheduling/cron-ticker#seed-with-the-chain-builder).
See [seed cron tickers](/docs/5.x/guides/scheduling/cron-ticker#seed-cron-tickers) for retries,
keys, validation, and how removed schedules are retired.

`[TickerFunction]` and `WithCron(...)` no longer accept a cron expression; passing one is a compile
error.

To keep the expression in configuration, pass a `%Section:Key%` placeholder:

```csharp
options.SeedCronTickers(crons => crons.Add("CleanupJob", "%CronSettings:Cleanup%"));
```

```json
{
  "CronSettings": {
    "Cleanup": "0 2 * * *"
  }
}
```

At startup, TickerQ reads `CronSettings:Cleanup` from `IConfiguration` and uses that value as the
expression. Startup fails when the key has no value or the value is not a valid expression, so the
key must exist on every replica.

## Group related functions

```csharp
builder.Services.MapTickerGroup("Maintenance", group =>
{
    group.WithMaxConcurrency(1);
    group.MapTicker<CleanupJob>("Cleanup");
});
```

This alternative registers the stable name `Maintenance.Cleanup`. Group defaults apply to each function separately; they do not create one shared concurrency limit for the group. `WithPriority` sets a default priority, and `WithLifetime(ServiceLifetime...)` sets the DI lifetime for classes registered in the group. A group is a naming convention, while an [application namespace](/docs/5.x/guides/configuration) separates runtime data in the store.

## Register a delegate

```csharp
builder.Services.MapTicker("Maintenance.Ping", (context, cancellationToken) =>
{
    cancellationToken.ThrowIfCancellationRequested();
    return Task.CompletedTask;
});
```

An overload also supplies the execution's `IServiceProvider`; resolve scoped dependencies there instead of capturing services from a request that has already ended. Delegate registrations can use `WithCron`, `WithPriority`, and `WithMaxConcurrency` too.

For a typed request, use `MapTicker<TRequest>` with a handler that receives `TickerFunctionContext<TRequest>`:

```csharp
builder.Services.MapTicker<InvoiceRequest>("Invoices.Ping", (context, cancellationToken) =>
{
    cancellationToken.ThrowIfCancellationRequested();
    var orderId = context.Request.OrderId;
    return Task.CompletedTask;
});

public record InvoiceRequest(Guid OrderId);
```

The `IServiceProvider` overload is available for typed delegates as well.

## Registration rules

- Use a unique, stable function name. Do not register the same function through both attributes and `MapTicker`.
- Keep registrations consistent across worker replicas of one namespace. A producer also needs the function/request contracts used to validate its scheduling calls.
- Normal managed .NET applications resolve typed request metadata automatically. Native AOT applications must register every request and declared result type through `WithJsonContext`; follow the [Native AOT guide](/docs/5.x/guides/native-aot).
- Confirm the resulting registry in **About → Functions**. A registered function is not proof that a cron definition is enabled or that a job has been created.
- For attributes and typed payloads, continue with [defining jobs](/docs/5.x/guides/defining-jobs) and [requests and results](/docs/5.x/guides/requests-results).
