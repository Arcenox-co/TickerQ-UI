Scheduler hosts require a stable application namespace. Configure it once on `AddTickerQ`. You do not put it on every time ticker or cron ticker. TickerQ manages the [reconciliation epoch](#reconciliation-epoch) itself.

```csharp
builder.Services.AddTickerQ(options =>
{
    options.UseLicense("licenses/tickerq.tqlicense");
    options.UseApplicationNamespace("orders-production");
    options.ConfigureScheduler(scheduler =>
    {
        scheduler.NodeIdentifier = "orders-worker";
        scheduler.NodeDisplayName = "Orders worker · EU 1";
        scheduler.AdvertisedDashboardUrl =
            "https://orders-eu-1.internal/tickerq/dashboard";
    });
    // Add your operational store and optional packages here.
});
```

## Schedule policy startup configuration

Register application-owned date providers and declare code-owned policies inside the same
`AddTickerQ` configuration:

```csharp
builder.Services.AddTickerQ(options => options
    .UseApplicationNamespace("orders-production")
    .AddScheduleDateProvider<PublicHolidayProvider>()
    .SeedSchedulePolicies(policies => policies
        .Add(SchedulePolicy.Create("Orders operating calendar")
            .InTimeZone("Europe/Tirane")
            .ExcludeDatesFrom("Public holidays"))));
```

Policies are seeded before cron and time tickers, so seeds can safely reference them. Seeding runs
when startup reconciles, not on every restart. A changed declaration changes the
[startup fingerprint](#reconciliation-epoch), so the next deployment applies it automatically.
Every scheduler replica needs the same date-provider names and behavior. Keep
provider evaluation local and deterministic; do not call remote calendar APIs from
`IScheduleDateProvider.IsExcluded`.

Policies are stored in the application namespace. Changing a node identifier does not create a
separate policy set. See [business calendars](/docs/5.x/guides/schedule-policies/business-calendars) for full definitions
and [storage upgrade](/docs/5.x/guides/storage-upgrade#add-schedule-policy-storage) before deploying
the new model to an existing database.

## A practical example

You run three Orders replicas and two Reporting replicas against one database:

| Deployment | Namespace | What it can execute |
| --- | --- | --- |
| Orders replica 1, 2, and 3 | `orders-production` | Jobs in the Orders runtime partition |
| Reporting replica 1 and 2 | `reporting-production` | Jobs in the Reporting runtime partition |
| Orders staging | `orders-staging` | Staging jobs only |

Replicas of one application use the **same namespace** and coordinate acquisition. A different namespace isolates time jobs, cron definitions/occurrences, and related runtime state. Namespaces are not worker names, and they are not a replacement for database credentials or a hostile-tenant security boundary.

The readable namespace is converted to a canonical storage identity. The built-in providers persist ownership using `ApplicationNamespaceKey` and scoped storage structures; the database key is not necessarily the literal display name. Manager calls stamp the configured runtime identity automatically. Do not manually move a stored job into another partition.

TickerQ trims the namespace and applies Unicode normalization (NFC), then compares it exactly. Matching is case-sensitive: `Orders-Production` and `orders-production` are different partitions. The value must be non-empty and at most 512 UTF-8 bytes. Changing the value later points the host at a new, empty partition; existing jobs stay under the old one. See [application namespace and identity](/docs/5.x/guides/troubleshooting#application-namespace-and-identity) for common symptoms.

## Which name goes where?

| Name | Set it on | Example |
| --- | --- | --- |
| Application namespace | `AddTickerQ` → `UseApplicationNamespace` | `orders-production`, shared by all Orders replicas |
| Node identifier | `ConfigureScheduler` → `NodeIdentifier` | `orders-worker-1`, a readable host label |
| Node display name | `ConfigureScheduler` → `NodeDisplayName` | `Orders worker · EU 1`, an operator-facing label |
| Function name | `[TickerFunction]` or `MapTicker` | `Orders.SendInvoice`, selected by each job |
| Job ID | Returned by the manager | One scheduled time job or one cron definition |

The same function name can appear in different application namespaces without allowing one namespace's scheduler to acquire the other's jobs. A namespace does not route work to one particular replica; replicas in that namespace cooperate.

## Node identifier

`NodeIdentifier` is the readable worker label. Execution ownership also includes a process ID and unique per-process value, so two processes with the same label cannot impersonate each other's leases. Keep the application namespace stable; each running host has its own execution owner.

`NodeDisplayName` supplies a friendlier dashboard label. `AdvertisedDashboardUrl` optionally gives operators a link to that node's dashboard; it is never used as a backend control endpoint. Node discovery and cross-node cancellation travel through the operational store. Read [nodes and cluster operations](/docs/5.x/dashboard/clustering).

## Reconciliation epoch

Startup reconciliation (repairing chains and applying seeded policies, crons, and time tickers) runs
once per deployment, not on every restart. TickerQ tracks deployments with a reconciliation epoch, a
number stored with the namespace's activation record. You do not configure it.

At startup each scheduler computes a **fingerprint** of its startup inputs:

- the TickerQ version;
- every registered function, with its request and result contracts;
- the declarations from `SeedSchedulePolicies`, `SeedCronTickers`, and `SeedTimeTickers`.

It then compares the fingerprint with the activation record:

| Fingerprint | What the host does |
| --- | --- |
| Same as the active deployment | Joins it. Restarts and extra replicas skip reconciliation. |
| Never seen | Claims the next epoch, reconciles, and activates it. Hosts still on the previous epoch stop acquiring work at that moment, so old and new code never process jobs side by side. |
| Seen before (an earlier deployment) | Starts fenced: the application runs, but it acquires no work. It takes over, and reconciles its own inputs, once no node has run the current epoch for 30 seconds. A stopping node reports this immediately. |

So a deploy that only changes code inside functions keeps running without interruption, while a
deploy that changes a request type, a function list, or a seed moves the whole namespace to the new
code at once. A rollback restores the earlier deployment's seeds once the newer nodes have stopped. Deploying a
build again after rolling back from it works the same way: its fingerprint is already known, so it
takes over once the other build's nodes have stopped.
An invalid seed declaration fails startup before any epoch is claimed, so the running deployment keeps
working.

The `UseSchedulePolicySeeder` and `UseTickerSeeder` callbacks are code, so they are not part of the
fingerprint. They run whenever an epoch is claimed. Prefer the declarative `Seed...` methods for
definitions the application owns.

### Manual epochs

`UseReconciliationEpoch(n)` takes manual control, for example when a release process already numbers
deployments. Every replica of one deployment then uses the same positive `n`. Keep it stable across
restarts and increase it whenever startup inputs change: a restart with an already-activated epoch skips
reconciliation, and logs a warning when its inputs differ. A host configured with a lower epoch than the
store's fails closed.

## Existing data

Changing the namespace does not automatically adopt old rows. Legacy ownership and first activation require an explicit rollout plan, particularly when several applications share a store. Follow the [storage upgrade reference](/docs/5.x/guides/storage-upgrade) rather than applying a catch-all adoption to a shared database.

## Separate producers and workers

A web API can accept work while a separate worker executes it. Give both applications the same namespace, durable store, and compatible function/request registrations. Disable background processing only on the producer:

```csharp
// In the producer's existing AddTickerQ configuration:
options.UseApplicationNamespace("orders-production");
options.DisableBackgroundServices();
// Add the same operational store used by the worker.
```

The worker keeps background services enabled and takes part in the [reconciliation epoch](#reconciliation-epoch). The producer can use `AddAsync` to save jobs, or EF `StageAsync` when it shares the application's business context. Use a persistent provider: two in-memory processes do not share a queue. `RunNowAsync` requires a running local dispatcher, so it is not a producer-only dispatch mechanism.

Queue-only processes do not perform scheduler activation. Their lack of an epoch does not remove the need for compatible schemas and contracts. Avoid the namespace-less legacy-global mode for new applications.
