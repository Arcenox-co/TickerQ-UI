A cron ticker is a schedule definition. Each run has a separate occurrence with its own status, timestamps, logs, and ID.

## Seed cron tickers

Declare the recurring schedules your application owns with `SeedCronTickers`. Register the function
as usual, then add its schedule to the list:

```csharp
builder.Services.AddTickerQ(options =>
{
    options.UseApplicationNamespace("billing-api");
    options.SeedCronTickers(crons => crons
        .Add("DailyInvoicesJob", "0 0 8 * * *")
        .Add("SendRemindersJob", "%Billing:RemindersCron%"));
});
```

Each entry names a registered function and a cron expression. Five-part and six-part expressions are
supported; six-part expressions put seconds first. A `%Section:Key%` placeholder is read from
configuration at startup. To compute expressions from services, use the overload that also receives
the application's `IServiceProvider`:

```csharp
options.SeedCronTickers((crons, services) =>
{
    var configuration = services.GetRequiredService<IConfiguration>();
    crons.Add("Reports.Export", configuration["Reports:ExportCron"]!);
});
```

### Seed with the chain builder

`Add("Function", "<cron>")` seeds a plain cron. For anything more, pass the same builder that
[`AddChainAsync`](/docs/5.x/guides/recurring-chains) uses. A single `StartWith(...)` is a plain cron;
`Then`, `ThenMany`, and the outcome steps make it a recurring chain:

```csharp
options.SeedCronTickers(crons => crons
    .Add(cron => cron
        .WithExpression("0 0 8 * * 1-5")
        .InTimeZone("Europe/Berlin")
        .UsingPolicy("Business hours")
        .SkipIfAlreadyRunning()
        .WhenMissed(MissedExecutionPolicy.SkipAfter(TimeSpan.FromMinutes(30)))
        .StartWith("Invoices.Prepare", new PrepareInvoicesRequest("daily"), step =>
        {
            step.Retries = 2;
            step.RetryIntervals = [300, 900];
            step.TimeoutSeconds = 600;
        })
        .ThenMany(branches =>
        {
            branches.Add("Invoices.Email");
            branches.Add("Invoices.Archive");
        })
        .ThenAfterAll("Invoices.Notify"))
    .Add("Invoices.Prepare:month-end", cron => cron
        .WithExpression("0 0 22 28 * *")
        .StartWith("Invoices.Prepare", new PrepareInvoicesRequest("month-end"))));
```

| Need | Builder call |
| --- | --- |
| Time zone | `InTimeZone("Europe/Berlin")`; without it, the scheduler time zone applies |
| [Schedule policy](/docs/5.x/guides/schedule-policies/business-calendars) | `UsingPolicy("Business hours")` |
| Request payload | `StartWith("Function", request)` or `StartWith<TFunction, TRequest>(request)` |
| Retries and timeout | The step options: `Retries`, `RetryIntervals`, `TimeoutSeconds`, `OnStale` |
| Late starts and catch-up | `WhenMissed(...)` and `CatchUp(...)`; see [late starts](/docs/5.x/guides/schedule-policies/late-starts) |
| Overlap | `SkipIfAlreadyRunning()` |
| Description | `WithDescription("...")` |
| Created disabled | `Enabled(false)` |
| Chain steps | `Then`, `ThenMany`, `ThenAfterAll`, `ThenAfterAnyFailed`, and the other outcome steps |

The key of a seeded cron defaults to the root function's name. Use `Add("key", cron => ...)` to run
one function on several schedules, as the month-end entry above does.

### How seeding avoids duplicates

Seeded crons are reconciled as one list when a deployment changes them. TickerQ fingerprints the
declarations, so the first host of a deployment with changed seeds reconciles, while restarts and
other replicas skip seeding. See [reconciliation epoch](/docs/5.x/guides/configuration#reconciliation-epoch).

- Each cron is stored once per key. A unique index on the application namespace and key prevents a
  second row, even when many replicas start together.
- A changed expression, time zone, policy, request, chain, retry setting, timeout, or late-start,
  catch-up, or overlap rule updates the existing row in place. Occurrences already queued under the
  old definition are skipped. A changed description only updates the row.
- `Enabled(false)` applies only when the cron is first created, so enabling or disabling it in the
  dashboard survives later reconciliations.
- A cron you remove from the list is disabled and marked retired after the grace period. It is not
  deleted, and declaring the same key again restores it.
- Crons created through the manager or the dashboard are never touched by seeding.

Advance the epoch when you change the list, an expression, or its configuration value. The
dashboard marks seeded crons **From code**. Edits made there to a seeded cron are replaced by the
declared values when the next epoch activates.

### Validation

Every seeded cron is validated with the same rules as `AddChainAsync` before anything is written.
Startup stops with the seed's key in the message when:

- a step names a function that is not registered, or its request does not match the function's
  contract, including a missing request for a function that requires one;
- the time zone is unknown;
- the schedule policy does not exist, or it never allows the expression;
- a `%Section:Key%` placeholder has no configuration value, or the expression is invalid;
- two seeds have the same key.

Schedule policies from `SeedSchedulePolicies` and `UseSchedulePolicySeeder` are seeded before crons,
so a seeded cron can use a seeded policy. A policy must exist by the time crons are reconciled; one that is created later, for
example in the dashboard, is not available to that startup.

### Moving from attribute schedules

`[TickerFunction]` and the code-first `WithCron(...)` no longer declare schedules. A cron argument on
either is a compile error. Remove it and add the schedule to `SeedCronTickers` with the same function
name:

```csharp
// Before
[TickerFunction("Invoices.Daily", "0 8 * * *")]

// After
[TickerFunction("Invoices.Daily")]
options.SeedCronTickers(crons => crons.Add("Invoices.Daily", "0 8 * * *"));
```

The default key is the function name, the identity attribute schedules already used, so the existing
row keeps its history, occurrences, and dashboard state. The deployment reconciles the new
declarations automatically.

## Dynamic schedule

Inject `ICronTickerManager<CronTickerEntity>` and create a schedule once:

```csharp
var result = await manager.AddAsync(new CronTickerEntity
{
    Function = "Invoices.Generate",
    Expression = "0 8 * * *",
    SkipIfAlreadyRunning = true,
    Retries = 2,
    RetryIntervals = [10, 30]
}, cancellationToken);

if (!result.IsSucceeded)
    throw result.Exception;
```

`UpdateAsync` changes an existing definition. `StageAsync` creates a new schedule as part of an [EF transaction](/docs/5.x/entity-framework/transactional-scheduling).

## Control a schedule

- `SetEnabledAsync(cronId, false)` pauses future scheduling; it does not stop a running occurrence or its published chain.
- `RunNowAsync(cronId)` creates a new manual occurrence without changing the expression or its next scheduled slot.
- `RerunOccurrenceAsync(occurrenceId)` revives an existing occurrence in place. A standalone occurrence keeps its ID; a recurring chain retries its existing durable graph.
- `RequestCancellationAsync(occurrenceId)` signals the running occurrence on the current host or sends a cancellation command to the node that owns it. Pass the occurrence ID, not the cron definition ID. See [cross-node cancellation](/docs/5.x/dashboard/clustering#cross-node-cancellation).

`RunNowAsync` and `RerunOccurrenceAsync` dispatch from the calling host. They fail when that host's scheduler is not running and licensed, for example on a host configured with `DisableBackgroundServices()`.

For a sequence of jobs on each run, add a [recurring chain template](/docs/5.x/guides/recurring-chains). For overlap rules and their host/cluster boundaries, see [cron overlap](/docs/5.x/guides/cron-overlap).

Each definition's `TimeZoneId` interprets its cron expression. Set it with `CronSchedule.InTimeZone(...)`, the recurring-chain builder's `InTimeZone(...)`, or the entity property; when it is null, the scheduler time zone applies. A seeded cron sets it with `InTimeZone(...)` on the builder. Changing the dashboard's display time zone only changes how timestamps are displayed.

## Time zones, calendars, and catch-up

Use `CronSchedule` when a recurring definition needs an explicit time zone, reusable schedule
policy, late-start limit, or downtime catch-up rule:

```csharp
var result = await manager.AddAsync<DailyInvoicesJob>(
    CronSchedule.From("0 8 * * 1-5")
        .InTimeZone("Europe/Tirane")
        .UsingPolicy("EU business hours")
        .WhenMissed(MissedExecutionPolicy.SkipAfter(TimeSpan.FromMinutes(10)))
        .CatchUp(CronCatchUpMode.RunLatest),
    cancellationToken);
```

The cron time zone produces candidate instants. The policy evaluates those candidates in its own
time zone and omits blocked occurrences. `WhenMissed` limits how late an occurrence that already
exists may enter user code. `RunLatest` addresses a different gap: it creates at most the newest
slot missed while no scheduler was available, provided that slot is still inside the bounded
`SkipAfter` window. The default catch-up mode is `Skip`.

These settings also belong on the root of a recurring-chain builder. Read
[business calendars](/docs/5.x/guides/schedule-policies/business-calendars) and [late starts and catch-up](/docs/5.x/guides/schedule-policies/late-starts) for the complete behavior and
[runtime reliability](/docs/5.x/guides/reliability#late-start-and-cron-catch-up) for failure and
recovery boundaries.

## Choose code or a dynamic definition

Use `SeedCronTickers` for a schedule owned by the deployed application. Use the manager or dashboard for schedules that operators create and change at runtime. Two definitions may call the same function; function-name equality does not deduplicate dynamic schedules. Save the returned definition ID and update that record.

A cron expression schedules future occurrences; it is not an unlimited backlog of every calendar
slot missed during downtime. Recovery handles existing overdue occurrences. `RunLatest` is an
explicit, bounded exception that creates only the newest qualifying missed slot. See
[runtime reliability](/docs/5.x/guides/reliability#late-start-and-cron-catch-up) and
[application identity](/docs/5.x/guides/configuration) before running multiple replicas.
