Inject `ITimeTickerManager<TimeTickerEntity>` or `ICronTickerManager<CronTickerEntity>` from `TickerQ.Utilities.Interfaces.Managers`. If your application uses custom ticker entities, use those same types in its manager interfaces.

## Choose by intent

| I need to… | Start here |
| --- | --- |
| Save a new job now | `AddAsync` |
| Build a sequential or parallel workflow | Time or cron `AddChainAsync` |
| Apply a calendar or late-start rule | Typed `AddAsync<TFunction>(TimeSchedule/CronSchedule, ...)` |
| Create or inspect a reusable calendar | `ISchedulePolicyManager` |
| Commit new work with my business transaction | `StageAsync` with the EF application context |
| Stop pending work before its handler runs | Time `CancelAsync` |
| Stop all pending work of one function | Time `CancelPendingAsync<TFunction>` |
| Move pending work to another time | Time `RescheduleAsync` |
| Wait for a job and read its result | `WaitForCompletionAsync`, or `GetOutcomeAsync` to check once |
| Show a cron's upcoming run times | Cron `GetNextOccurrencesAsync` |
| Read or list existing jobs or crons | `GetAsync`, `ListAsync`, `ListAsync<TFunction>` |
| Delete every job or cron matching a filter | `DeleteAsync(filter)` |
| Ask a running handler to stop | `RequestCancellationAsync`; forwarded to the owning node when needed |
| Repeat work immediately | `RunNowAsync`, then inspect its persisted outcome |
| Retry a settled chain from one step | Time `RetryFromAsync` |
| Re-run one existing cron occurrence | Cron `RerunOccurrenceAsync` |
| Remove old history automatically | [Job retention](/docs/5.x/guides/retention) |

## Time ticker operations

| Method | Behavior |
| --- | --- |
| `AddAsync(entity, ct)` | Validate and persist a new job or complete chain independently |
| `AddChainAsync(chain => ..., ct)` | Build a [one-time chain](/docs/5.x/guides/job-chaining) with the fluent builder and persist it like `AddAsync` |
| `StageAsync(entity, ct)` | Track a new job/chain in the same scoped EF application context as business data; caller saves and commits |
| `UpdateAsync(entity, ct)` | Update an eligible job; this is not a direct status setter |
| `ReplaceChainAsync(rootId, newRoot, ct)` | Validate and replace an eligible complete graph atomically, preserving the original if replacement fails |
| `RunNowAsync(rootId, ct)` | Acquire an eligible root for execution now; does not reset an entire chain |
| `RetryFromAsync(id, ct)` | Reuse the existing chain identity, preserve completed ancestors and unaffected group branches, and reset the selected/affected downstream path; returns the chain root |
| `RescheduleAsync(id, executionTime, ct)` | Move a root that has not started to a new time, applying its schedule policy; fails for chain steps and for work that is queued, running, or finished |
| `CancelAsync(id, ct)` | Cancel an Idle/Queued job and its pending descendants; preserve records |
| `CancelPendingAsync<TFunction>(ct)` | Cancel every Idle/Queued standalone job and chain root of that function, with their pending steps |
| `GetOutcomeAsync(id, ct)` | Read the stored status, failure, and published result; `null` when the job does not exist |
| `WaitForCompletionAsync(id, timeout, ct)` | Wait until the job finishes or the timeout passes, then return its outcome |
| `RequestCancellationAsync(id, ct)` | Signal one running execution on this host, or send a cancellation command to the node that owns it |
| `SetDeleteBehaviorAsync(rootId, behavior, ct)` | Change the root's chain-deletion policy |
| `GetAsync(id, ct)` | Read one job with its chain steps; `null` when it does not exist |
| `ListAsync(ct)` / `ListAsync(filter, ct)` / `ListAsync<TFunction>(ct)` | List standalone jobs and chain roots, newest first, with steps in `Children` |
| `DeleteAsync(id, ct)` | Remove an eligible job/chain, subject to ownership and deletion checks |
| `DeleteAsync(filter, ct)` | Remove every matching job/chain that is safe to delete; see [read and delete in bulk](#read-and-delete-in-bulk) |

`AddBatchAsync`, `UpdateBatchAsync`, and `DeleteBatchAsync` are also available. Batch atomicity depends on the operation and provider; do not assume multiple independent calls form one transaction. Use [EF staging](/docs/5.x/entity-framework/transactional-scheduling) for new jobs that must commit with business data.

Typed `AddAsync<TFunction>(TimeSchedule, ct)` and
`AddAsync<TFunction, TRequest>(TimeSchedule, request, ct)` preserve the same manager result contract
while adding policy, blocked-time, and missed-execution settings. See
[business calendars](/docs/5.x/guides/schedule-policies/business-calendars) and [late starts and catch-up](/docs/5.x/guides/schedule-policies/late-starts).

## Cron operations and identifiers

| Method | Identifier / behavior |
| --- | --- |
| `AddAsync(entity, ct)` | Create a recurring definition, optionally with a chain template |
| `AddChainAsync(chain => ..., ct)` | Create a definition with a [recurring chain](/docs/5.x/guides/recurring-chains) template from the fluent builder |
| `StageAsync(entity, ct)` | Stage a new definition in the scoped EF application context |
| `UpdateAsync(entity, ct)` | Update the schedule definition |
| `SetEnabledAsync(cronId, enabled, ct)` | Pause/resume future scheduling; running work continues |
| `RunNowAsync(cronId, ct)` | Create a fresh manual occurrence; return its occurrence ID |
| `RerunOccurrenceAsync(occurrenceId, ct)` | Re-run the existing occurrence in place; standalone runs keep the occurrence ID and recurring chains retry their existing graph |
| `RequestCancellationAsync(occurrenceId, ct)` | Signal that running occurrence on this host or its owning node; do not pass its definition ID |
| `GetNextOccurrencesAsync(cronId, count, ct)` | List the next 1–1,000 run times in UTC, applying the cron's time zone and schedule policy; empty while it is disabled |
| `GetOutcomeAsync(occurrenceId, ct)` | Read an occurrence's stored status, failure, and published result |
| `WaitForCompletionAsync(occurrenceId, timeout, ct)` | Wait until the occurrence finishes or the timeout passes, then return its outcome |
| `GetAsync(cronId, ct)` | Read one definition; `null` when it does not exist |
| `ListAsync(ct)` / `ListAsync(filter, ct)` / `ListAsync<TFunction>(ct)` | List definitions, seeded ones included |
| `DeleteAsync(cronId, ct)` | Delete an eligible definition; this is not an occurrence cancellation operation |
| `DeleteAsync(filter, ct)` | Delete matching definitions with their occurrences; seeded crons are kept |

Cron managers also support add/update/delete batches and typed `AddAsync<TFunction>` overloads. A recurring-chain occurrence is a dispatcher: after its chain is launched, manage the resulting time jobs individually.

Use `AddAsync<TFunction>(CronSchedule, ct)` or its typed-request overload for an explicit time zone,
schedule policy, late-start rule, or catch-up mode. String-expression overloads remain supported for
simple definitions.

## Schedule policy operations

Inject `ISchedulePolicyManager` to manage namespace-scoped calendar definitions:

| Method | Behavior |
| --- | --- |
| `ListAsync(ct)` / `GetAsync(id, ct)` | Read policies and their current revisions |
| `CreateAsync(policy, ct)` | Create a uniquely named policy |
| `UpsertAsync(policy, ct)` | Create or reconcile the policy with the same normalized name |
| `UpdateAsync(policy, expectedVersion, ct)` | Update rules using optimistic concurrency; returns `null` when the revision changed. Names cannot change |
| `DeleteAsync(id, expectedVersion, ct)` | Delete only when no ticker or policy references it; throws while referenced |
| `EvaluateAsync(name, instant, ct)` | Explain whether one UTC instant is allowed |
| `FindNextAllowedAsync(name, instant, ct)` | Find the next allowed instant |
| `PreviewCronAsync(...)` | Preview allowed and blocked cron candidates without creating occurrences |

Declare code-owned definitions with [`SeedSchedulePolicies(...)`](/docs/5.x/guides/schedule-policies/business-calendars). Use
`CreateAsync`/`UpdateAsync` for operator-owned policies created through application code. The
dashboard uses the same manager contract and passes the displayed revision as `expectedVersion`.

## Interpret the result

Most mutations return `TickerResult<T>`. Always check the operation before using its output:

```csharp
var run = await cronTickerManager.RunNowAsync(cronId, cancellationToken);
if (!run.IsSucceeded)
    throw run.Exception;

var occurrenceId = run.Result.Id;
```

`EnsureSuccess()` does the same check in one call. It rethrows the failure with its original stack trace, or returns the result so you can keep using it:

```csharp
var occurrenceId = (await cronTickerManager.RunNowAsync(cronId, cancellationToken)).EnsureSuccess().Result.Id;
```

| Member | Meaning |
| --- | --- |
| `IsSucceeded` | The manager operation succeeded; it is not a job completion status |
| `Exception` | Failure details when `IsSucceeded` is false |
| `Result` | Returned entity when that operation provides one |
| `AffectedRows` | Provider-reported change count for operations that return counts |

Time `RunNowAsync` returns an affected count without a result entity. Cron `RunNowAsync` returns the new occurrence. Time `RetryFromAsync` returns the chain's root entity with `AffectedRows` set to 1, and cron `RerunOccurrenceAsync` returns the existing occurrence.

Delete, cron update, `CancelAsync`, and `RequestCancellationAsync` calls can succeed with zero affected rows; inspect the count when it is relevant. Time `UpdateAsync`, `SetDeleteBehaviorAsync`, and `SetEnabledAsync` instead return a failed result when nothing was changed. Batch counts can include descendants and need not equal the number of roots submitted.

`StageAsync` is different: it returns the tracked entity and **throws** on invalid input or unsupported configuration. It has not persisted anything until you save and commit the context.

Once a mutation commits, a failed dashboard refresh notification does not undo it. Avoid blindly repeating a creation call after an uncertain network response: it may create another job. Make business effects idempotent as described in [reliability](/docs/5.x/guides/reliability).

## Wait for a job and read its result

`GetOutcomeAsync` and `WaitForCompletionAsync` return a `TickerOutcome` with the job's `Status`,
`IsCompleted`, `IsSucceeded`, `ExecutedAt`, `ExceptionMessage`, and `SkippedReason`. When the job
succeeded and called `SetResult`, `HasResult` is true and `GetResult<T>()` reads the value:

```csharp
var added = await timeManager.AddAsync<ExportJob>(DateTime.UtcNow, cancellationToken);
if (!added.IsSucceeded)
    throw added.Exception;

var outcome = await timeManager.WaitForCompletionAsync(added.Result.Id, TimeSpan.FromMinutes(2), cancellationToken);
if (outcome is { IsSucceeded: true, HasResult: true })
{
    var export = outcome.GetResult<ExportSummary>();
}
```

A job counts as completed once it is Done, DueDone, Failed, Cancelled, or Skipped; retries happen
before that. After the timeout the method returns the latest stored outcome, so check `IsCompleted`
rather than catching an exception. It returns `null` when the job does not exist, for example after
[retention](/docs/5.x/guides/retention) removed it. The store is polled, starting at 100 ms and
backing off to once a second, so it works whichever replica runs the job. A chain root completes
before its steps run; wait on the step whose result you need. In a Native AOT application, use
`GetResult(typeInfo)` with source-generated serializer metadata.

For a cron, pass the occurrence ID, for example the one returned by `RunNowAsync`, not the cron's ID.

## Read and delete in bulk

`ListAsync` returns standalone jobs and chain roots, with each chain's steps in `Children`. A filter is matched against roots only, so a filter on a step's function finds nothing unless its root also matches. Reads cover only this application's [namespace](/docs/5.x/guides/configuration#separate-environments). Large stores return every match, so filter as narrowly as you can.

```csharp
var pendingExports = await timeManager.ListAsync(
    x => x.Function == "ExportJob" && x.Status == TickerStatus.Idle, cancellationToken);
var reportCrons = await cronManager.ListAsync<ReportJob>(cancellationToken);
```

`DeleteAsync(filter)` deletes each matching job together with its chain steps, whatever its status, so finished and failed history goes too. It skips work that is running or leased, and chains whose `Restrict` policy still protects unfinished steps. `AffectedRows` counts every deleted job, steps included. Pass `_ => true` to delete everything that is safe to delete:

```csharp
(await timeManager.DeleteAsync(_ => true, cancellationToken)).EnsureSuccess();
(await timeManager.DeleteAsync(
    x => x.Function == "ReportJob" && x.Status == TickerStatus.Done, cancellationToken)).EnsureSuccess();
(await cronManager.DeleteAsync(x => x.Function == "ReportJob", cancellationToken)).EnsureSuccess();
```

The cron overload deletes definitions with their occurrences, but keep crons declared with [`SeedCronTickers`](/docs/5.x/guides/scheduling/cron-ticker#seed-cron-tickers): their code owns them, so remove them from the seed instead. To stop jobs without deleting their history, use `CancelPendingAsync<TFunction>` or `SetEnabledAsync`.

## Run, retry, and cancel on demand

Time and cron `RunNowAsync`, `RetryFromAsync`, and `RerunOccurrenceAsync` dispatch the work from the calling host. That host's scheduler must be running and licensed; otherwise the call returns a failed result with an `InvalidOperationException`. A host configured with `DisableBackgroundServices()` therefore cannot perform these operations. Call them on a scheduler node. Success means the execution was accepted, not that it completed.

`RetryFromAsync` accepts any step of a settled chain: every job in the chain must be terminal, with no acquisition owner or live lease. The chain can contain at most 1,000 jobs, and the selected step can be at most 50 levels deep, counting the root. Larger graphs are rejected.

`RescheduleAsync` reads the job and saves the new time only if its stored state still matches, so a job
that starts while it is being moved is reported as changed rather than moved. Reschedule a chain by
its root; steps run after their parent.

`CancelPendingAsync<TFunction>` covers jobs and chain roots of that function. Steps of the function
inside other chains are left alone; cancel those chains with `CancelAsync`. Cron definitions keep
creating occurrences, so pause them with `SetEnabledAsync`. `AffectedRows` counts every cancelled
job, chain steps included.

`RequestCancellationAsync` first signals a matching execution on the current host. If the execution runs elsewhere and the provider supports cluster control, the manager writes a cancellation command for the owning node. The command expires after about 30 seconds. All built-in providers (EF Core, MongoDB, Redis, and in-memory) support this; in-memory storage only reaches hosts that share its process state. `AffectedRows` is 1 when the local signal or the command was accepted and 0 when no running execution could be targeted. Neither result proves that the function has exited. See [cross-node cancellation](/docs/5.x/dashboard/clustering#cross-node-cancellation).

## Seed one-time work

Declare startup work with [`SeedTimeTickers`](/docs/5.x/guides/scheduling/time-ticker#seed-one-time-work), which creates one ticker per key. Use a seeder callback only when the work depends on logic the declaration builder cannot express. Seeder callbacks run whenever startup reconciles, which happens when a deployment's startup inputs change; changing only the callback does not trigger it. `AddAsync` and `AddChainAsync` have no key, so a seeder that calls them adds another job each time.

To seed recurring schedules, use [`SeedCronTickers`](/docs/5.x/guides/scheduling/cron-ticker#seed-cron-tickers) rather than a cron seeder. Cron manager `AddAsync` has no key, so a cron seeder adds another copy each time startup reconciles; `SeedCronTickers` keeps one row per key and retires schedules you remove.

On a scheduler host, manager mutations wait until startup activation completes. Do not await them before `app.Run()`, because activation only starts with the host and the call would never return. Put startup work in `UseTickerSeeder`, or run it after the application has started. See [a manager call never returns](/docs/5.x/guides/troubleshooting#a-manager-call-never-returns).
