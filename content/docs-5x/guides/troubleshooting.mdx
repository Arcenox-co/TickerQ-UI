## A job is not running

| Check | What to verify |
| --- | --- |
| License | The certificate is present and valid on every worker |
| Scheduler | The host is running, startup activation completed, and `DisableBackgroundServices()` is not enabled on every process |
| Function | The exact persisted function name exists in **About → Functions** |
| Runtime identity | Producers and workers use the same application namespace and store; worker replicas use the intended epoch |
| Time | `ExecutionTime` is UTC; a cron uses the scheduler time zone, not the dashboard display zone |
| Capacity | Worker slots and any per-function permits are available |
| Persisted state | EF staging was saved and committed; the job was not cancelled, skipped, or already acquired |

A five-part cron such as `* * * * *` is supported, including configuration references. Six-part expressions place seconds first. Verify the resolved configuration value and next run; an empty or invalid value should be investigated in startup diagnostics.

Startup reconciliation runs under a deployment epoch. Restarting a changed binary with an already-activated epoch does not apply its new manifest. Advance the epoch for changed definitions or contracts using your [rollout plan](/docs/5.x/guides/storage-upgrade).

## A cron run is missing or skipped

Inspect the occurrence's skip reason and the definition's enabled state. An overlap policy can skip a new run while an earlier run or chain remains unfinished. Optional startup stale-occurrence skipping deliberately discards eligible old runs.

Recovery can execute persisted overdue occurrences, but TickerQ does not manufacture an occurrence for every cron slot missed while all hosts were offline. Use a business-level reconciliation job if every business period must be accounted for.

## A chain says Waiting after its root finished

The table summarizes the entire chain. Open the branch icon and inspect unfinished descendants, their run conditions, execution times, and available capacity. A root's **Done** status is not a statement that all its children are done. A failure branch runs only for the corresponding parent outcome.

A child with its own `ExecutionTime` is scheduled independently; leave that field unset for a normal parent continuation. A skipped conditional branch is terminal and counts toward finished steps.

## Cancellation was accepted but work continues

`CancelAsync` applies to pending time jobs. `RequestCancellationAsync` signals running work on the current host and returns zero affected rows when that host does not own it. A handler must observe its cancellation token and pass it to asynchronous dependencies. Timeouts also request cooperative cancellation; the runtime cannot forcibly terminate arbitrary .NET code.

## Logs are missing or disappear after restart

Use `ILogger` within the execution scope; `Console.WriteLine` is not captured. Check host logging filters, `MinimumLevel`, capture limits, and truncation notices. Memory-only tails disappear on restart. Persistence requires a supported operational store, its schema, and `PersistToDatabase = true`.

Diagnostics separates read availability from background-write failures. A successful read does not prove recent lines were stored. Database outages, full buffers, retention, and hard shutdown can lose lines. See [execution logs](/docs/5.x/guides/execution-logs).

## An integration did not send an alert

1. Check the connection and rule are enabled and the function/event filters match. Ordinary event rules do not notify on every retry or successful run.
2. Inspect **Integrations → Activity**, failed attempts, cooldown suppression, and queue drops. Event-alert activity is node-local; monitoring keeps separate persistent delivery state.
3. For monitors, check their current state, baseline, time zone, and retained history. Recovery requires the condition's recovery criteria, not just a successful HTTP send.
4. Confirm replicas share their Data Protection application name and key ring. A key-ring mismatch prevents reading saved settings.
5. Investigate endpoint rejection or host allow-list restrictions without logging webhook URLs or authorization headers.

Sending a test checks the saved destination's delivery path. It does not prove a particular rule or monitor will match. See [monitoring](/docs/5.x/integrations/monitoring) and [delivery behavior](/docs/5.x/integrations/delivery).

## A migration or activation fails

Apply the application's generated migration before scheduler startup. Inspect the reported epoch, unsupported schema version, ambiguous legacy owner, or malformed chain instead of clearing metadata or deleting history to bypass the error. MongoDB scheduler mode requires transactions; Redis Cluster scheduler mode is unsupported. The [storage upgrade reference](/docs/5.x/guides/storage-upgrade) describes safe remediation and adoption boundaries.

## Login succeeds but dashboard access or controls are wrong

Check that host authentication is registered before `AddTickerQ` and its middleware runs before `UseTickerQ`. The named dashboard policy must exist and accept the user's actual claims. Read-only predicates return true to block writes; integration management needs a separate positive grant.

If API calls authenticate but the browser has the wrong controls, verify that normal navigation and the runtime configuration script also receive the host session. Basic/custom API authentication does not automatically populate a role-bearing `HttpContext.User`. Check role-claim mapping, refresh the session after database role changes, and reload the page to refresh its privately cached configuration.

An integration **Management access required** message can mean missing management permission or read-only mode. HTTP 403 on writes can also come from the license gate. If job lists load but live changes do not, inspect SignalR authentication and the proxy's WebSocket routing. See [existing users](/docs/5.x/dashboard/existing-users) and [roles and permissions](/docs/5.x/dashboard/authorization).

## Prepare a useful issue report

Include the full TickerQ package versions, .NET/EF/provider versions, topology, number of replicas, relevant sanitized configuration, job/occurrence IDs, timestamps with time zone, and a minimal reproduction. Explain the expected behavior and the persisted outcome. Omit certificates, API keys, connection strings, and webhook credentials.
