TickerQ replicas cooperate through the configured operational store. The dashboard's **Clustering → Nodes** page shows the scheduler processes currently known in the active application namespace.

## Configure node identity

```csharp
builder.Services.AddTickerQ(options =>
{
    options.UseApplicationNamespace("orders-production");
    options.UseReconciliationEpoch(12);

    options.ConfigureScheduler(scheduler =>
    {
        scheduler.NodeIdentifier = "orders-worker";
        scheduler.NodeDisplayName = "Orders worker · EU 1";
        scheduler.AdvertisedDashboardUrl =
            "https://orders-eu-1.internal/tickerq/dashboard";
    });
});
```

| Setting | Meaning |
| --- | --- |
| `NodeIdentifier` | Readable logical role. Several replicas may intentionally share it. |
| `NodeDisplayName` | Optional friendlier label shown to operators. |
| `AdvertisedDashboardUrl` | Optional navigation link for this node's dashboard. |
| Execution owner ID | Process-unique internal owner generated by TickerQ; do not configure it. |

`AdvertisedDashboardUrl` is only an operator link. TickerQ never sends backend control requests to it, so it can be a private hostname, ingress address, or omitted. It must be an absolute HTTP(S) URL without credentials.

## What the Nodes page shows

Each heartbeat can report the friendly name, logical identifier, TickerQ version, registered function count, scheduler state, running and queued attempts, capacity, function waits, retry delays, process start time, and last heartbeat. Offline entries are visually muted and remain available briefly for diagnosis.

Heartbeats are partitioned by `ApplicationNamespace`. Two applications sharing a database but using different namespaces do not discover or control each other's nodes. Nodes from one namespace are paged in the dashboard rather than rendered as an unbounded card list.

Inactive node records and completed command records are pruned after approximately one day. The active/offline threshold is shorter and is based on heartbeat freshness; retention does not imply that an old node is still reachable.

## Cross-node cancellation

Cancellation from the dashboard or from `RequestCancellationAsync` on the time and cron managers first signals a matching execution in the responding process. Only when nothing local matched does TickerQ route the request to the owning process. It does not make an HTTP call to that process; it writes a short-lived command into the shared operational store:

1. The request resolves the persisted execution owner and acquisition generation. A command is written only when that record is `Queued` or `InProgress` and has an owner.
2. A command targets the process-unique node key.
3. The owning process polls, verifies that the same attempt is still active, and cancels its local `CancellationTokenSource`.
4. A stale command cannot cancel a later retry or rerun of the same job.

Delivery normally takes up to one second. Cancellation remains cooperative: the function must observe its `CancellationToken`. Commands expire after 30 seconds.

The built-in EF Core, MongoDB, and Redis providers support separate-process discovery and control. In-memory discovery is limited to hosts sharing the same process state. Custom providers can implement `ITickerQClusterControlStore`; otherwise ordinary scheduling still works, but Nodes and cross-node cancellation are unavailable.

EF Core requires `TickerQNodes` and `TickerQControlCommands` in the application-owned migration. See the [storage upgrade guide](/docs/5.x/guides/storage-upgrade#add-node-discovery-and-control-tables).

## Scheduler clustering versus dashboard live updates

The operational provider coordinates job ownership, node discovery, and cross-node cancellation. It does not automatically distribute SignalR messages between dashboard processes. These are separate channels:

| Channel | Purpose | Multi-replica requirement |
| --- | --- | --- |
| Operational store | Job state, ownership, node heartbeats, and control commands | Use one supported store and application namespace across the intended replicas |
| SignalR | Browser hints that refresh dashboard data | Configure a backplane for immediate delivery across dashboard replicas |

Without a SignalR backplane, scheduling and cancellation still use the shared operational store correctly. A browser connected to another replica can receive a live hint late and is repaired by the bounded consistency refresh. Configure Redis or Azure SignalR through [`ConfigureSignalR(...)`](/docs/5.x/dashboard#signalr-in-multi-replica-deployments) when immediate cluster-wide dashboard updates matter.

## Show the deployment environment

Set a dashboard-only environment label so operators can distinguish Development, Staging, and Production before signing in or running an action:

```csharp
options.AddDashboard(dashboard =>
{
    dashboard.SetTitle("Orders");
    dashboard.SetEnvironmentName(builder.Environment.EnvironmentName);
});
```

The label appears in the dashboard identity and sign-in experience. It does not change the scheduler namespace or isolate data. Use `UseApplicationNamespace(...)` for runtime partitioning.
