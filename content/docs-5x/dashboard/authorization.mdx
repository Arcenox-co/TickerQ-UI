TickerQ uses your application's permissions through three configuration points. Start with [existing users](/docs/5.x/dashboard/existing-users) to connect your identity system, then choose roles or claims to make these decisions.

| Decision | Configuration | Effect |
| --- | --- | --- |
| Who can access scheduler data? | `WithHostAuthentication("PolicyName")` | Requires the authenticated host user and named authorization policy |
| Who can change jobs or control the scheduler? | `SetReadOnly(context => ...)` | A `true` result disables mutation controls and rejects protected writes |
| Who can configure outbound integrations? | `AllowIntegrationManagement(context => ...)` | Requires a separate positive grant; denied by default |

`SetReadOnly` is a restriction: return **true for viewers**, not operators. `AllowIntegrationManagement` is a grant: return **true for integration administrators**. `SetReadOnly(true)` overrides the per-user write decision for everyone. License restrictions also remain in force.

## Roles or permission scopes

Use the [role example](/docs/5.x/dashboard/existing-users#connect-your-existing-sign-in-flow) when your application has viewer, operator, and administrator roles. If your identity provider issues permissions or OAuth scopes, map those to the same dashboard controls.

The following alternative uses three **application-defined** permissions:

| Permission | Meaning in this example |
| --- | --- |
| `scheduler.read` | Enter the dashboard and inspect scheduling data |
| `scheduler.write` | Perform dashboard mutations, provided `scheduler.read` is also granted |
| `scheduler.integrations.manage` | Manage integrations, provided both read and write access are also granted |

TickerQ does not issue these scopes or recognize their names automatically. Configure them in your identity system. Use this policy and dashboard configuration instead of the role-based example:

```csharp
builder.Services.AddAuthorization(authorization =>
{
    authorization.AddPolicy("SchedulerOperators", policy => policy
        .RequireAuthenticatedUser()
        .RequireAssertion(context =>
            SchedulerPermissions.Has(context.User, "scheduler.read")));
});

// Inside your existing AddTickerQ registration:
options.AddDashboard(dashboard =>
{
    dashboard.WithHostAuthentication("SchedulerOperators", "/account/login");
    dashboard.SetReadOnly(context =>
        !SchedulerPermissions.Has(context.User, "scheduler.write"));
    dashboard.AllowIntegrationManagement(context =>
        SchedulerPermissions.Has(context.User, "scheduler.integrations.manage"));
});
```

Add this helper to your application. It accepts individual `permission` claims and space-separated `scope` or `scp` values from authenticated identities, comparing complete values rather than substrings:

```csharp
using System.Security.Claims;

public static class SchedulerPermissions
{
    public static bool Has(ClaimsPrincipal user, string permission) =>
        user.Identities
            .Where(identity => identity.IsAuthenticated)
            .SelectMany(identity => identity.Claims)
            .Any(claim =>
                (claim.Type == "permission" &&
                    string.Equals(claim.Value, permission, StringComparison.Ordinal)) ||
                ((claim.Type == "scope" || claim.Type == "scp") &&
                    claim.Value.Split(' ', StringSplitOptions.RemoveEmptyEntries)
                        .Contains(permission, StringComparer.Ordinal)));
}
```

Match the claim types to your issuer's actual, validated principal. For example, `scheduler.write.extra` must not grant `scheduler.write`. If `IsInRole` does not match a role in your JWT, check the host's `RoleClaimType` mapping; do not weaken the policy. Microsoft documents [name and role claim mapping](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/claims?view=aspnetcore-10.0).

## What the dashboard enforces

| Area | Browser behavior | Server behavior |
| --- | --- | --- |
| Job and scheduler operations | Read-only mode hides mutation controls, including create, edit, delete, run, retry, cancel, and host controls | The protected mutation group rejects writes with HTTP 403 |
| Integrations | Without writable management access, the page shows **Management access required** | Save, preview, and send-test require management permission, write access, and the license gate |
| Integration configuration reads | Users without management access do not receive saved configuration | The read endpoint returns availability without loading the stored settings when management is not granted |
| AI assistant, when configured | Viewers can ask questions; mutation proposal tools are unavailable in read-only mode | Tools use the same read-only decision; integration context requires its management permission |
| Live updates | Authenticated viewers can follow job changes | The hub validates authentication and the configured host policy when a connection opens |
| Assistant conversations | Users can manage their own stored conversations, including in read-only mode | Conversation endpoints use the resolved history identity; they are separate from scheduler mutations |

A management grant does not override read-only mode. If you deliberately grant management to a read-only user, the API can return the management snapshot, but the current Integrations page still shows the access-required state and rejects changes. Leave the management grant false when that user should not receive integration configuration.

The browser receives its read-only state through a per-user runtime configuration script; the server re-evaluates write permissions on each request. Authenticate in the host pipeline **before** `UseTickerQ` so both requests see the same user. Hiding buttons is not the authorization boundary.

## Permission changes and account restrictions

Changing a database role does not automatically rewrite an already-issued cookie or JWT. Use your identity system's principal refresh, security-stamp validation, token lifetime, or session revocation mechanisms. If you need a fresh database decision, perform it asynchronously in your host authorization/claims pipeline; dashboard permission predicates are synchronous.

After changing permissions, refresh the host session and reload the dashboard. The runtime configuration can be cached privately for 60 seconds, so its controls may briefly reflect the previous session. The API still applies its current request's permissions. An already-connected SignalR session is not continuously re-authorized; account restrictions that require immediate live-data revocation need a host-managed disconnect/reconnect strategy.

## Access boundaries

These controls cover dashboard entry, all dashboard writes, and integration management. There is no built-in per-function, per-job-owner, per-tenant, or individual run/delete permission matrix. Read-only users can still inspect the runtime's job details, requests, results, and retained logs.

Assistant history has additional [identity and storage boundaries](/docs/5.x/dashboard/ai-assistant#conversation-and-proposal-history); shared credentials do not create separate personal histories.

An OAuth permission scope is also different from an [application namespace](/docs/5.x/guides/configuration): the former authorizes a user; the latter partitions scheduler storage and workers. A namespace is not a user-level data filter.

Before publishing the dashboard, verify a denied user, a viewer, an operator, and an integration administrator. Test both browser controls and a direct API request. Check live updates and repeat after a role change; successful login alone does not verify authorization.
