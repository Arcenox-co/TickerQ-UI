The dashboard brings scheduling, execution history, and runtime configuration into your application. This tour uses **real screenshots from the local 5.x demo hosts**, including the chains, database logs, integration monitoring, and simulated-error examples. Counts and timestamps are sample activity, not performance benchmarks. Workspace names and certificate identifiers are anonymized.

Select any screenshot to open the full-size image. See [dashboard setup](/docs/5.x/dashboard) to add the dashboard to your host, and [authentication](/docs/5.x/dashboard/authentication) before exposing it outside local development.

## Chain view

Follow connected steps and inspect each job's status, duration, and details. Click a step to open its details and logs. The table's aggregate status and the selected step's status answer different questions:

| Chain label | Meaning |
| --- | --- |
| Running | At least one step is in progress |
| Waiting | Unfinished steps remain, but none is in progress |
| Done | All steps are terminal, with no failures or cancellations; skipped branches can still be present |
| Finished with errors / cancellations | All steps are terminal and the chain contains failures or cancellations |
| Chain unavailable | The dashboard could not build a complete chain summary |

Progress counts all terminal steps, including skipped, failed, and cancelled steps. It is not a count of successful steps. Open the chain to see which branches ran.

## Integrations

The optional `TickerQ.Integrations` package adds connections, alert rules, monitoring, and delivery activity. Connection secrets are never displayed back in the dashboard.

<DashboardScreenshot name="integrations" alt="Integrations connections tab with a configured Slack destination" caption="Reuse a saved connection across rules and monitors. Sending a test is an explicit action." />

### Alert rules

Choose which events and functions should notify a destination. This separates the connection details from the conditions that trigger a message.

<DashboardScreenshot name="alert-rules" alt="Alert rules tab showing function and event routing to Slack" caption="Route relevant events to the people who need them." />

### Monitoring

Configure monitors for repeated failures, long-running executions, or completion deadlines. Each monitor shows its current state and can send a recovery message after a successful execution confirms that the condition has cleared. This is separate from alerts for individual failure events.

<DashboardScreenshot name="monitoring" alt="Two demo monitors for consecutive failures and long-running execution with recovery alerts enabled" caption="The demo monitors inspect function executions and send their alerts through the Slack connection." />

Customize job alerts, monitor alerts, and recovery messages separately. Preview the message using sample data before saving. Previewing does not deliver a webhook.

## Live updates and ownership

The dashboard uses SignalR notifications to refresh affected data. It reconnects and restores cron subscriptions after a disconnect. Active chains also refresh approximately every two seconds, and a visible active log tail refreshes approximately every 1.5 seconds; these browser refreshes are separate from scheduler timing.

If a view stops updating, check the browser's hub connection, authentication, and reverse-proxy support for the dashboard hub route. Host status refreshes every five seconds, but that does not mean every table has a universal polling fallback.

A job's **Node** field displays the configured node name. Its tooltip shows the full execution-owner identifier, including the process ID and instance suffix. The owner identifies the process that acquired the job; it is not the application's namespace or a count of workers. Scheduler controls and Diagnostics refer to the responding application instance.

## AI assistant

The optional assistant can inspect runtime data and propose supported actions for confirmation. Your host supplies the AI provider. See [AI assistant setup and capabilities](/docs/5.x/dashboard/ai-assistant).

Open **AI → Chat AI**, select a suggested question, or type a request in the composer. Answers stream into the conversation. Proposed changes appear as action cards that you review and confirm or dismiss.
