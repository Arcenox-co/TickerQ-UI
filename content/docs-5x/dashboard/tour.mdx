The dashboard brings scheduling, execution history, and runtime configuration into your application. This tour uses **real screenshots from two local 5.x demo nodes** sharing one migrated SQLite store. The fixture includes time and cron jobs, grouped chains, database logs, saved work, cluster state, integrations, and AI investigations. Counts and timestamps are sample activity, not performance benchmarks. Workspace names and certificate identifiers are anonymized.

Select any screenshot to open the full-size image. See [dashboard setup](/docs/5.x/dashboard) to add the dashboard to your host, and [authentication](/docs/5.x/dashboard/authentication) before exposing it outside local development.

## Time tickers

Browse one-time jobs, search by function, and filter standalone jobs or chains. Select a row to inspect that job. The chain badge opens its workflow. Jobs created by a recurring cron chain appear under the cron occurrence, keeping this list focused on time tickers.

The create flow can run a new function or chain as an ephemeral test before saving it. Use **Save draft** to retain unfinished one-time work without creating an `Idle` ticker.

<DashboardScreenshot name="time-tickers" alt="Time tickers table showing waiting, completed, failed, and chained jobs" caption="Waiting is the dashboard label for persisted Idle work; chain badges summarize the whole workflow." />

## Saved work

Saved work separates non-executable drafts from reusable chain templates. Search and order saved definitions, open a draft to edit its inherited execution time, or update a template in place. Activating a draft asks you to keep or change its time and publishes the graph once through a durable activation claim.

Read [drafts, templates, and activation](/docs/5.x/dashboard/saved-work).

### Visual chain builder

## Chain view

Follow connected steps and inspect each job's status, duration, and details. Click a step to open its details and logs. The table's aggregate status and the selected step's status answer different questions:

| Chain label | Meaning |
| --- | --- |
| Running | At least one step is in progress |
| Waiting | Unfinished steps remain, but none is in progress |
| Done | All steps are terminal, with no failures or cancellations; skipped branches can still be present |
| Finished with errors / cancellations | All steps are terminal and the chain contains failures or cancellations |
| Chain unavailable | The dashboard could not build a complete chain summary |

Progress counts all terminal steps, including skipped, failed, and cancelled steps. It is not a count of successful steps. Open the chain to see which branches ran.

Durable parallel groups appear as containers rather than fake function cards. Their branches stay inside the group, and a single merge rail leads to the success, failure, cancellation, or all-terminal outcomes. Edge colors describe the condition path; job cards keep the execution-status colors. Select a settled step to preview **Retry from this job**, or select the group to rerun all grouped branches.

### Job details and logs

The details panel shows the selected job's status, duration, durable progress, request payload, parent ID, input from the parent's committed result, the job's output result, and available logs when those values exist. IDs have a copy action and parent links stay inside the same flowchart.

Exception details prioritize the application frame and source line, while generated and TickerQ scheduler frames stay out of the primary trace. Failed and cancelled executions show **Investigate with AI** in the details header when the assistant is configured. Scheduler lifecycle messages sit alongside application log messages. A database log tail can remain available after a restart when persistence is configured.

## Live updates and ownership

The dashboard uses SignalR notifications to refresh affected data. It reconnects and restores cron subscriptions after a disconnect. Active chains also refresh approximately every two seconds, and a visible active log tail refreshes approximately every 1.5 seconds; these browser refreshes are separate from scheduler timing.

If a view stops updating, check the browser's hub connection, authentication, and reverse-proxy support for the dashboard hub route. Host status refreshes every five seconds, but that does not mean every table has a universal polling fallback.

A job's **Node** field displays the configured node name. Its tooltip shows the full execution-owner identifier, including the process ID and instance suffix. The owner identifies the process that acquired the job; it is not the application's namespace or a count of workers. Scheduler controls and Diagnostics refer to the responding application instance.

## Nodes

Open **Clustering → Nodes** to compare replicas in the current application namespace: heartbeat state, version, registered functions, execution capacity, running/queued attempts, waits, retries, and start time. Offline nodes are muted and the list is paged. An advertised dashboard URL is an operator link only; cross-node cancellation uses a durable store command rather than an HTTP request.

Read [nodes and cluster operations](/docs/5.x/dashboard/clustering).

## AI Operations

The optional assistant has Overview, Chat, and Investigations views. It can inspect runtime data, diagnose one failed or cancelled execution, retain review states, and propose supported actions for confirmation. Optional automatic investigation uses a shared namespace budget and coordination lease so replicas do not purchase the same diagnosis concurrently. Your host supplies the AI provider and decides whether source excerpts are available.

<DashboardScreenshot name="assistant-overview" alt="AI Operations overview with unread diagnoses, recovery signals, and repeated failures" caption="Overview summarizes investigation activity and recent operational evidence." />

<DashboardScreenshot name="assistant-investigations" alt="Investigations page grouping repeated diagnoses while retaining each execution" caption="Repeated failures can reuse one diagnosis without losing per-execution review state." />

Open **AI → Chat AI**, select a suggested question, or type a request in the composer. Answers stream into the conversation. Proposed changes appear as action cards that you review and confirm or dismiss.

<DashboardScreenshot name="assistant-conversation" alt="Chat AI continuing from a saved failed-execution investigation" caption="Continue in chat keeps follow-up questions scoped to the selected execution and its current evidence." />

## Reproduce the screenshots

The [`TickerQ.Docs.Demo`](https://github.com/Arcenox-co/TickerQ/tree/main/samples/TickerQ.Docs.Demo) sample is the source for this tour. It uses the current project references, a real EF Core migration, database execution logs, saved definitions, integrations, cluster state, and a deterministic local assistant client. Start two nodes against one SQLite database, sign in with the sample credentials, then call its `/demo/seed` endpoint to recreate the fixture. The sample README contains the exact commands and explains which records deliberately fail or remain paused.
