The dashboard can inspect and operate your scheduler. Configure authentication before exposing it. Startup rejects missing authentication unless you explicitly call `AllowAnonymousDashboard()`.

## Choose an authentication mode

| Mode | Configuration | Behavior |
| --- | --- | --- |
| Host authentication | `WithHostAuthentication(policy, loginRedirectPath)` | Reuses your application's authenticated user and authorization policy |
| HTTP Basic | `WithBasicAuth(username, password)` | Validates Basic credentials; an async validator overload is also available |
| API key | `WithApiKey(key)` or `WithApiKey(key, headerName)` | Validates a static key from Bearer authorization or your named header |
| Dashboard JWT or cookie login | `WithAuthentication(auth => ...)` | Issues signed sessions using explicitly configured users and signing keys |
| Custom authentication | `WithCustomAuth(...)` | Uses your header validator or async `HttpContext` validator; request-scoped database services are available |

Basic authentication and API keys **do not issue dashboard JWTs**. The JWT/cookie login endpoints exist only when those issuing schemes are configured. Use HTTPS for credentials and keep secrets outside source control. Choose host authentication for individual application users and their roles; the other modes serve applications that deliberately manage dashboard access separately.

`WithAuthentication(auth => ...)` can register multiple schemes. They are tried in registration order until one succeeds; adding schemes is not a way to require multiple credentials or MFA. Use a single host identity policy when combining access requirements.

### Register schemes with `WithAuthentication`

The `auth` builder exposes one method per scheme:

| Method | Scheme |
| --- | --- |
| `AddHost(policy, loginRedirectPath)` | Host authentication; both arguments are optional |
| `AddBasic(username, password, configure)` or `AddBasic(validator, configure)` | HTTP Basic with a fixed pair or an async `(username, password)` validator |
| `AddApiKey(key)` or `AddApiKey(key, headerName)` | Static key from the `Authorization` header, or from the named header |
| `AddCustom(Func<string, bool>)` or `AddCustom(Func<HttpContext, Task<bool>>)` | Validator for the raw `Authorization` value, or an async request validator |
| `AddJwtBearer(...)` / `AddCookieLogin(...)` | [Dashboard-issued sessions](#built-in-jwt-sessions) |

The optional `BasicAuthOptions` callback sets `ChallengeBrowserPrompt` and `Realm`. `ChallengeBrowserPrompt` defaults to false, so a failed request returns a plain 401 for the SPA login page. When true, the 401 also carries `WWW-Authenticate: Basic realm="…"` for non-browser clients and direct browser navigations to dashboard API routes, so a browser can show its native prompt; the SPA's own fetch requests still receive a plain 401. `Realm` defaults to `TickerQ Dashboard` and is also part of a Basic user's [assistant history identity](/docs/5.x/dashboard/ai-assistant#conversation-and-proposal-history).

```csharp
dashboard.WithAuthentication(auth => auth
    .AddHost("SchedulerOperators", "/account/login")
    .AddApiKey(builder.Configuration["TickerQ:Dashboard:ApiKey"]!, "X-Api-Key"));
```

### Do not mix single-mode methods

`WithHostAuthentication(...)`, `WithBasicAuth(username, password)`, `WithApiKey(key)`, and `WithCustomAuth(Func<string, bool>)` each select a single mode. That mode is applied at startup **only when no other scheme is registered**. If you also call `WithAuthentication(...)`, `WithBasicAuth(validator)`, `WithApiKey(key, headerName)`, or `WithCustomAuth(Func<HttpContext, Task<bool>>)`, the single-mode method could never take effect, so startup fails with an `InvalidOperationException` that names the selected mode. Calling two single-mode methods keeps only the last one, and calling `AllowAnonymousDashboard()` after one of them clears it. To combine schemes, register all of them inside `WithAuthentication(...)`.

## Existing users, roles, and scopes

For database-backed application users, use **host authentication**. It reuses your sign-in flow and authenticated principal, including roles and claims. It does not require copying users into dashboard configuration.

- [Use existing users](/docs/5.x/dashboard/existing-users): connect ASP.NET Core Identity or your own user store, configure the host pipeline, and support browser sessions and live updates.
- [Roles and permissions](/docs/5.x/dashboard/authorization): grant viewer, operator, and integration-administrator access using roles, permission claims, or OAuth scopes.

`SetReadOnly(true)` makes the dashboard read-only for everyone. The predicate overload supports per-user restrictions with server-side enforcement. `AllowIntegrationManagement` is a separate permission and defaults to denied. Neither bypasses license restrictions.

### Read-only predicates with built-in schemes

The `context.User` examples in these guides assume host authentication. The dashboard's own schemes (Basic, API key, custom, JWT, and cookie login) do not populate `HttpContext.User`. After a dashboard API request authenticates, TickerQ stores the result in `context.Items["auth.username"]` and `context.Items["auth.userId"]`; a predicate for these schemes must read those items:

```csharp
dashboard.SetReadOnly(context =>
    context.Items["auth.username"] as string != "operator");
```

API keys report the username `api-user` and custom validators report `custom-user`, so for those schemes `auth.username` does not identify individual users. The items are set only on authenticated API requests. The runtime-configuration script that drives the browser's controls is served before dashboard authentication, so the predicate sees no username there. With the example above, every browser shows read-only controls, while API writes from `operator` are still accepted. Use host authentication when per-user browser controls matter.

## Built-in JWT sessions

Use this alternative when you deliberately want dashboard-issued credentials instead of host authentication:

```csharp
dashboard.WithAuthentication(auth => auth.AddJwtBearer(jwt =>
{
    jwt.SetSigningKey(builder.Configuration["TickerQ:Dashboard:SigningKey"]
        ?? throw new InvalidOperationException("Dashboard signing key is required."));
    jwt.AddUser(
        builder.Configuration["TickerQ:Dashboard:Username"]
            ?? throw new InvalidOperationException("Dashboard username is required."),
        builder.Configuration["TickerQ:Dashboard:Password"]
            ?? throw new InvalidOperationException("Dashboard password is required."));
    jwt.AccessTokenLifetime = TimeSpan.FromMinutes(60);
}));
```

Supply a strong signing secret of at least 32 bytes from a secret store. Replicas must share the key, issuer, audience, and user configuration. `AddCookieLogin(...)` provides the equivalent signed-cookie option, with `SessionLifetime` and `AddUser`. Cookie sessions default to eight hours; Bearer access tokens default to 60 minutes. Both option types expose `Issuer` (default `tickerq-dashboard`) and `Audience` (default `tickerq-api`). `CookieAuthOptions.CookieName` defaults to `tickerq.auth`, and the cookie is scoped to the dashboard path.

Registering both `AddJwtBearer` and `AddCookieLogin` creates one shared token issuer. The bearer options supply its issuer, audience, access-token lifetime, and user store, and also its signing key when one is set. The cookie's own expiry still follows `SessionLifetime`, but the JWT inside it expires after `AccessTokenLifetime`, so a cookie session ends after `AccessTokenLifetime` unless it is renewed, even when `SessionLifetime` is longer.

For local development only, `AllowEphemeralSigningKey = true` permits a random process-local key. Tokens then stop working after restart or when routed to another instance. This option is not enabled automatically, even for a single server. The built-in user store is configured by the application; it is not a user-management or SSO service.

### Renewal and logout

With JWT/cookie login configured, paths are relative to the dashboard base path:

| Endpoint | Behavior |
| --- | --- |
| `POST /api/auth/login` | Validate configured credentials and issue a session |
| `POST /api/auth/refresh` | Renew from a still-valid token; expired tokens require login |
| `POST /api/auth/logout` | Clear the auth cookie; the browser also discards its stored Bearer token |

Renewal is sliding access-token renewal. There is no durable refresh-token store or per-token revocation. Client logout does not revoke an already-issued Bearer token. Keep lifetimes appropriate to your access policy; use your host identity system when you need its session-management capabilities.

Set `AccessTokenLifetime` on `AddJwtBearer(...)` or `SessionLifetime` on `AddCookieLogin(...)` to control session length.

Cookies are HttpOnly and SameSite=Strict. `SecureCookie` defaults to true; disable it only for a plain-HTTP local demo. Login endpoints limit failures to five per five-minute window, using separate IP and username buckets. These limits are process-local; use edge controls when you need shared protection across replicas. A throttled request returns 429 with `Retry-After`.

## Reverse proxies and cross-origin access

Forwarded headers are disabled unless trusted proxies or networks are configured:

```csharp
dashboard.TrustForwardedProxy(System.Net.IPAddress.Parse("10.0.0.4"));
// Or a network that is actually controlled by your deployment:
// dashboard.TrustForwardedNetwork(System.Net.IPNetwork.Parse("10.0.0.0/24"));
```

These methods enable forwarded headers. Calling `EnableForwardedHeaders()` without a trust list fails validation. Trust only your actual proxy addresses so clients cannot choose their reported IP, host, or scheme.

For a split-origin deployment, configure exact browser origins:

```csharp
dashboard.SetBackendDomain("https://api.example.com");
dashboard.AllowOrigins("https://ops.example.com");
```

`SetBackendDomain` selects the API domain; it does not grant CORS access. Calling it without `AllowOrigins(...)` or `SetCorsPolicy(...)` fails at startup. Origins must be absolute HTTP(S) origins with no extra path, query, or fragment. Cross-origin access is denied by default. `SetCorsPolicy(...)` supports custom policies; retain a deliberate credentialed-origin boundary.

## SignalR and reverse proxies

The hub is mounted beneath the dashboard base path at `tickerq-notification-hub`. The SPA reads that route from runtime configuration, so a custom `SetBasePath(...)` or host `UsePathBase(...)` remains aligned as long as the proxy preserves the public prefix.

Browsers cannot attach a normal `Authorization` header to the WebSocket or Server-Sent Events APIs. SignalR therefore uses `access_token` in the query string for those transports. TickerQ accepts that query credential only on the exact hub route. Use HTTPS and redact `access_token` from ingress, proxy, tracing, and request logs.

Configure the proxy to:

- forward WebSocket `Upgrade` and `Connection` headers;
- disable response buffering for Server-Sent Events;
- keep the upstream read timeout longer than SignalR's keep-alive interval;
- retain session affinity when multiple application replicas use a Redis backplane; and
- allow the exact browser origin when the dashboard and API use different origins.

Multi-replica message delivery also needs a SignalR backplane. See [dashboard SignalR configuration](/docs/5.x/dashboard#signalr-in-multi-replica-deployments). Microsoft documents the platform requirements in its [SignalR hosting and scaling guidance](https://learn.microsoft.com/en-us/aspnet/core/signalr/scale?view=aspnetcore-10.0).

## Dashboard middleware hooks

Three optional properties add middleware inside the dashboard's own request branch, beneath its base path:

| Property | Runs |
| --- | --- |
| `PreDashboardMiddleware` | After trusted forwarded headers are applied, before static files, the runtime-configuration script, routing, and dashboard authentication |
| `CustomMiddleware` | After dashboard authentication, before dashboard API endpoints and the SignalR hub |
| `PostDashboardMiddleware` | After endpoint mapping, so only for requests that no dashboard endpoint handled, before the SPA fallback |

```csharp
dashboard.PreDashboardMiddleware = app => app.Use(async (context, next) =>
{
    context.Response.Headers["X-Frame-Options"] = "DENY";
    await next();
});
```

These hooks do not replace your host pipeline. Host authentication still requires `UseAuthentication()` and `UseAuthorization()` before `UseTickerQ()`.

## Local anonymous access

```csharp
dashboard.AllowAnonymousDashboard();
```

This exposes dashboard data and permitted operations to anyone who can reach it. Use it only for an isolated local demo or when an independently configured access layer protects the endpoint. Read-only mode limits mutations but does not make job data public-safe.

Before production, verify the unauthenticated path, a read-only user, and an operator through the real proxy. Ensure live updates work, keep Data Protection keys persistent/shared when using integrations, and confirm application logs do not expose credentials. Dashboard settings are described in the [setup guide](/docs/5.x/dashboard).
