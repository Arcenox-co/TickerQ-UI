Use the assistant to investigate scheduler data, review saved diagnoses, and prepare changes for human approval. It uses the same dashboard authentication and authorization as other views. It is an optional feature of `TickerQ.Dashboard`; there is no separate AI package.

## AI Operations workspace

The **AI Operations** page has three views:

| View | Purpose |
| --- | --- |
| **Overview** | Unread investigations, diagnoses completed today, detected recoveries, recent failures, and repeated function/classification patterns |
| **Chat** | Streaming operational assistant, saved conversations, and confirmation cards |
| **Investigations** | Searchable, namespace-scoped diagnoses with Unread, Read, and Resolved review states |

Opening an investigation marks it read. Resolving it records an operator review state; it does not change the underlying execution. Repeated investigations for the same function are grouped visually, newest first, while each execution remains individually selectable and deletable.

<DashboardScreenshot name="assistant-investigations" alt="Grouped AI investigations with review state, repeated diagnosis count, and source evidence" caption="Repeated failures are grouped by function while every execution keeps its own review state and evidence." />

## Use Chat AI

1. Open **AI → Chat AI** in the dashboard sidebar.
2. Select a suggested question to send it immediately, or type your own request. Press **Enter** to send and **Shift+Enter** for a new line.
3. Read the answer as it streams, then ask a follow-up in the same conversation. Include the function name or execution ID when you want to inspect a particular job, or choose **Continue in chat** on a saved investigation.
4. If the assistant proposes a change, review the action card before applying it. Asking a question does not apply a proposed change.

The starting questions cover failed jobs, execution logs, registered functions, scheduler health, and integrations. The model label below **Chat AI** comes from the host configuration; provider selection and credentials are configured on the server.

## Inspect data and propose changes

The assistant can inspect registered functions and their request contracts, executions,
cron definitions, chain steps, retained execution logs, and node-local runtime health.
With integration-management permission and `TickerQ.Integrations` configured, it can
also inspect destinations, rules, monitoring state and recent delivery outcomes.
Webhook URLs, headers, message templates and delivery response bodies are excluded
from integration tool results.

The assistant drafts review cards for:

- One-time job and chain drafts, plus cron schedules and recurring chains.
- Cron schedule updates, including enabling/disabling a schedule.
- Execution retries, cancellation, and deletion.
- New alert rules and deadline, long-running or consecutive-failure monitors, using
  existing integration destinations and optional recovery notifications.

| Goal | Example request |
| --- | --- |
| Investigate a failure | “Read the logs for the most recent failed execution.” |
| Find available handlers | “Which registered functions can I schedule?” |
| Draft a recurring workflow | “Run Prepare then Publish every weekday at 08:00.” |
| Monitor repeated failures | “Alert Operations if GenerateInvoices fails three times.” |
| Set a completion deadline | “Monitor GenerateInvoices: finish by 08:00 Europe/Belgrade, with ten minutes of grace and a recovery message.” |

Replace the example function and destination names with ones configured in your application. The assistant works with registered handlers and existing integration destinations.

## Confirm operational changes

Action cards show the relevant function or chain steps, schedule and time zone, request payload, target execution, or alert destination. Check these details and any warning before continuing. To adjust a proposal, ask for a revised version in the conversation; cards do not have an inline editor.

| Control or result | Meaning |
| --- | --- |
| **Save draft** | Store a non-executable one-time job or chain draft for review |
| **Open draft** | Open a saved draft in the visual builder; activation remains a separate confirmation |
| **Confirm** | Apply the proposed operation through the dashboard API |
| **Confirm deletion** | Permanently delete the proposed target after reviewing the warning |
| **Request cancellation** | Ask a running handler to stop using its cancellation token |
| **Dismiss** | Leave the proposal unapplied; the card becomes **Dismissed** |
| **Applied** | The API accepted the operation; this does not mean a scheduled job has finished |
| **Requested** | A running cancellation request was accepted; check execution status for the outcome |

**Changes require an explicit action on the card.** Model tools never write data or send test messages. If confirmation fails, the dashboard displays **Failed to apply** and leaves the card pending.

One-time job and one-time chain cards save a [non-executable draft](/docs/5.x/dashboard/saved-work). Review and edit that draft in the builder, then activate it separately. This prevents an assistant-created proposal from becoming runnable immediately. Cron schedules and recurring chains use their own confirmation cards because they create or update cron definitions.

Confirmation uses the normal authenticated dashboard APIs, including their read-only,
license and integration-management checks. Execution cards recheck observed status
and execution timestamps before submitting; the underlying APIs still enforce current
state. Integration proposals retain the configuration version and fail on concurrent
edits. Read-only users receive no proposal tools.

A running cancellation requests cooperation through the handler's cancellation token;
it does not prove that the job stopped. Re-running a cron occurrence revives that exact
occurrence. A time-ticker retry reuses the selected stored execution; chain-specific
**Retry from this job** operations preview and reset only the affected downstream path.
Deletion cards explain their permanent effect. Monitors track individual function executions,
including chain steps, rather than completion of a whole workflow.

Cron proposals show the scheduler time zone. Deadline monitors have their own explicit
time zone. Configure new destinations and edit webhook secrets/templates in Integrations.

## Configure a chat client

The assistant uses your server-side `Microsoft.Extensions.AI.IChatClient`. Register a provider adapter that supports chat and tool calls in the host, then pass that client through the existing dashboard builder. This snippet assumes an `IChatClient` is already registered in DI; it does not configure a provider or API key by itself:

```csharp
using Microsoft.Extensions.AI;
using Microsoft.Extensions.DependencyInjection;
using TickerQ.Dashboard.DependencyInjection;

options.AddDashboard(dashboard =>
{
    dashboard.AddAssistant(ai => ai
        .UseChatClient(serviceProvider => serviceProvider.GetRequiredService<IChatClient>())
        .WithMaxToolIterations(8));
    // Optional: reuse your host application's authorization policy.
    dashboard.AllowIntegrationManagement(context => context.User.IsInRole("Admin"));
});
```

## Provider settings

Keep API credentials in server configuration or a secret store. `WithModelName(...)` changes the label shown in the chat panel; the model is selected when constructing your `IChatClient`. `WithMaxToolIterations(...)` limits tool round-trips per turn, not your provider's token budget. An unreachable provider, invalid credentials, or exhausted quota still prevents a reply even when the dashboard reports that the assistant is configured.

`UseChatClient` resolves its factory once from the root service provider. Supply a client suitable for singleton use; do not capture scoped database services. The dashboard wraps it for tool invocation and disposes the resulting client with the application. `WithSystemPrompt(...)` replaces the default prompt; preserve the instructions about untrusted tool data, read-only behavior, and explicit confirmation if you customize it.

## Conversation and proposal history

With server-side history enabled, the conversation sidebar lists saved chats. Select a title to reopen it, choose **New chat** for a fresh conversation, or delete a conversation after confirmation. Starting a new chat does not undo an operation already applied through an action card.

TickerQ stores proposal cards with the exchange when the history store supports `IAssistantProposalHistoryStore`. Reopening a conversation restores pending, dismissed, failed, and applied cards, including the **Open draft** link returned after a one-time draft is saved. Conversation text alone is never proof that an operation ran; the card state and current scheduler data remain authoritative.

Without a registered server history store, the dashboard keeps a bounded browser-local transcript and proposal list. It is scoped by the stable authenticated user, backend origin, and dashboard mount. Anonymous or unresolved identities do not inherit another user's transcript, and logging out clears the active local session. **New chat** clears the current local conversation.

EF Core can retain conversations, cards, and structured investigations by opting in on the operational store:

```csharp
// Inside the existing options.AddOperationalStore(store => { ... }) callback:
store.AddAssistantHistory(history =>
{
    history.MaxConversationsPerUser = 50;
    history.MaxMessagesPerConversation = 80;
    history.MaxInvestigationsPerNamespace = 500;
    history.InvestigationRetention = TimeSpan.FromDays(30);
    history.ReadInvestigationRetention = TimeSpan.FromDays(14);
    history.ResolvedInvestigationRetention = TimeSpan.FromDays(7);
});
```

The current EF model includes `AssistantConversations`, `AssistantMessages`, `AssistantInvestigations`, `AssistantInvestigationLeases`, and `AssistantInvestigationBudgets` even before this runtime option is enabled. Generate and apply the current application migration once; `AddAssistantHistory()` then enables persistence, coordination, and cleanup without changing schema shape. Assistant storage remains separate from execution-log persistence.

`InvestigationRetention` is the fallback lifetime measured from creation. `ReadInvestigationRetention` and `ResolvedInvestigationRetention` are optional state-specific lifetimes measured from the time an operator enters that state. Leave either value unset or non-positive to use the fallback. Cleanup is bounded and does not call the model.

Conversation history is private to a stable authenticated identity. Host authentication must provide `sub` or `ClaimTypes.NameIdentifier`; the key also includes the issuer and authentication scheme. Dashboard-issued cookie and bearer sessions share their issuer-scoped subject. A custom `IAuthService` should return a stable `AuthResult.UserId`. Anonymous sessions and identities without a stable subject can chat but do not persist history.

Investigations are operational records shared by authorized dashboard users in the same TickerQ application namespace. Treat stored conversation and diagnosis text as application data because it can contain the runtime information discussed with the assistant.

## Investigate one execution

Failed and cancelled time jobs and cron occurrences expose **Investigate with AI** in the job-details header. A failed chain summary targets the failed child execution rather than diagnosing only its successful root. You can also give Chat AI an exact execution ID, including for a skipped execution.

The investigator assembles a bounded evidence set:

- status, timing, retries, and current/last node holder;
- the structured exception and application source frames captured by TickerQ;
- up to 50 retained log lines;
- up to 50 related workflow steps;
- an optional source excerpt supplied by the application.

Request payload values are deliberately excluded. Exception, log, source, and function text is treated as untrusted evidence rather than model instructions. The saved diagnosis separates confirmed evidence from inference and a suggested next action.

Select **Continue in chat** to open a conversation scoped to that investigation. Follow-up questions keep the saved diagnosis as context and can re-read live execution evidence when needed. A general chat such as “Why are my jobs failing?” can return suggested investigation cards; it does not silently choose an unrelated old failure.

## Add bounded source context

For development, or a deployment that deliberately ships the matching source revision, allow-list local files explicitly:

```csharp
var revision = Environment.GetEnvironmentVariable("GIT_COMMIT_SHA")
    ?? "local-working-tree";

dashboard.AddAssistant(assistant => assistant
    .UseChatClient(chatClient)
    .ConfigureRunInvestigator(investigator => investigator
        .UseLocalSourceContext(builder.Environment.ContentRootPath, source => source
            .WithRepository("Orders API")
            .WithRevision(revision)
            .WithContextLines(before: 20, after: 20)
            .MapFunction("Payments.Charge", "Jobs/PaymentJob.cs")
            .MapSourceFile("InvoiceJob.cs", "Jobs/InvoiceJob.cs"))
        .WithSourceContextLimits(maximumLines: 60, maximumCharacters: 10_000)
        .RedactEvidenceWith(RedactApplicationSecrets)));
```

The local provider never searches the checkout. Paths must be relative to the configured root and cannot traverse outside it. Function mappings take precedence over filename mappings, which avoids ambiguity when several projects contain `Program.cs`.

For a private repository, register an application-owned `IExecutionSourceContextProvider`. The adapter receives the safe function, exception type, method, filename, and line; it can use host-owned GitHub/GitLab credentials, SourceLink artifacts, or an internal source service to return a small excerpt from an immutable revision. TickerQ does not need the repository token, does not clone a repository, and never exposes repository credentials to the browser.

## Automatic investigations

Automatic investigation is opt-in because it sends evidence to the configured model provider without waiting for an operator click:

```csharp
dashboard.AddAssistant(assistant => assistant
    .UseChatClient(chatClient)
    .WithModelName("operations-model")
    .ConfigureRunInvestigator(investigator => investigator
        .EnableAutomaticInvestigations(automatic => automatic
            .Every(TimeSpan.FromSeconds(30))
            .WithLookback(TimeSpan.FromMinutes(15))
            .WithBatchSize(10)
            .WithHourlyLimit(30)
            .WithCoordinationLease(TimeSpan.FromMinutes(5))
            .IncludeCancellations()
            .DetectSuccessfulRecovery())));
```

Only terminal failures with exhausted retries are investigated. Cancellations are excluded unless enabled. Each sweep has a bounded lookback and batch size.

Automatic investigation requires a durable `IAssistantInvestigationStore` and `IAssistantInvestigationCoordinator`; EF `AddAssistantHistory()` supplies both. Before calling the model, one node acquires a renewable database lease for the evidence fingerprint and consumes the shared rolling hourly budget. Other healthy nodes cannot purchase the same diagnosis concurrently. A crashed owner's work becomes recoverable after the configured lease period.

Repeated failures at the same application source line reuse the latest completed diagnosis in that namespace. TickerQ creates a new investigation record for the new execution, but copies the diagnosis without another model call or hourly-budget charge. The fingerprint includes the function, terminal status, exception type, safe source filename, and line. When no application frame exists, it also includes the normalized exception message so unrelated failures are not grouped together.

A later successful execution can mark older diagnoses as **Recovered** evidence. Recovery does not automatically resolve the operator review state. Deleting a diagnosis leaves a durable suppression marker for that execution, so a later automatic sweep does not immediately recreate the deleted item.

The coordination lease prevents simultaneous calls from healthy replicas. It cannot prove whether a provider billed a request if the process exits after the provider accepts it but before the response is committed; that attempt remains counted in the shared hourly budget.

## Data sent to the model and request limits

Logs and job data inspected by the assistant are sent to your configured model provider
and may appear in conversation history. Apply your application's log redaction and
model/data policies accordingly. Log reads verify that the execution belongs to the
current runtime and return at most 100 retained lines and 24,000 characters; retention,
truncation and storage availability can limit what the assistant sees. Request contracts
are capped at 12,000 characters. The chat request sets a maximum output of 1,500 tokens; provider behavior and billing remain provider-specific. Chat requests use up to the last 20 individual user/assistant messages, with a 128 KB body
limit and limits of 16,384 characters per message and 65,536 in total. AI proposals cap
chains at 100 steps, ten levels, and five children per step.

## Troubleshoot the assistant

| Symptom | Check |
| --- | --- |
| AI assistant is not configured | Register an `IChatClient` and pass it to `AddAssistant` |
| Configured, but no reply | Check the provider's credentials, endpoint, quota, and host logs using the error reference |
| Answers work, but no action cards appear | Check read-only permissions and whether the provider supports tool calls |
| Integration information is unavailable | Enable `AddIntegrations` and grant integration-management access |
| A proposal is rejected when confirmed | Reload current job/configuration state and check write, license, and integration permissions |
| Logs are missing or incomplete | Check execution-log retention, truncation, and storage availability; missing logs do not establish a successful run |
| Investigations are unavailable | Enable a durable assistant history store and apply its migration |
| Automatic investigation starts on more than one node | Verify every node uses the same namespace and shared coordinator tables, and that clocks are synchronized |
| A source excerpt is missing | Check the allow-list mapping, immutable revision, file path, source line, and redaction callback |

The assistant cannot deploy application code, register a missing function handler, configure webhook credentials, or send test messages. Use the application's normal deployment process and the Integrations editor for those tasks.
