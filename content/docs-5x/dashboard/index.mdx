Add `TickerQ.Dashboard` alongside core and register it inside `AddTickerQ`. The default dashboard is served at `/tickerq/dashboard` after `app.UseTickerQ()`.

[Take the visual dashboard tour](/docs/5.x/dashboard/tour) for screenshots of each view, including chains, execution logs, diagnostics, and integrations.

## Use your host authentication

```csharp
using TickerQ.Dashboard.DependencyInjection;

// Inside your existing AddTickerQ configuration:
options.AddDashboard(dashboard =>
{
    dashboard.SetTitle("Orders");
    dashboard.WithHostAuthentication("SchedulerOperators");
});
```

Reuse your application's database users, cookies, JWTs, or OIDC sign-in. Configure the host's authentication scheme and `SchedulerOperators` authorization policy before `AddTickerQ`, then run authentication/authorization middleware before `UseTickerQ`. The [existing-users guide](/docs/5.x/dashboard/existing-users) includes a full role-based example; [roles and permissions](/docs/5.x/dashboard/authorization) also covers permission claims and scopes.

For a loopback-only local demo, explicitly opt into `dashboard.AllowAnonymousDashboard()`. Anyone who can reach an anonymous dashboard can operate its jobs. The production choices and signing-key requirements are covered in [authentication and deployment](/docs/5.x/dashboard/authentication).

## Find what you need

| View | Use it for |
| --- | --- |
| Overview | Recent and upcoming work, with links to job details |
| Time tickers | One-time jobs and their chains |
| Cron tickers | Recurring definitions, human-readable expressions, and occurrences |
| Saved work | One-time drafts and reusable time/cron chain templates |
| Schedule policies | Reusable business calendars, previews, and the jobs that reference them |
| Executions and chain view | Per-run status, progress, ownership, requests/results, errors, and logs |
| Diagnostics | Runtime warnings, health, and recovery information |
| Integrations | Connections, alert rules, monitoring, and delivery feedback |
| Nodes | Scheduler replicas, capacity, queue pressure, heartbeats, and navigation links |
| AI Operations | Chat, saved investigations, automatic diagnoses, and reviewed action cards |
| License | Certificate and entitlement status |
| About | Registered functions, scheduler settings, retention, and execution-log configuration |

Actions such as cancellation, deletion, cron enable/disable, and scheduler start/stop require confirmation. Start/stop controls apply to the responding scheduler host; they are not a cluster-wide pause switch.

The chain badge summarizes the root and all descendants. It shows **Running** while any step is in progress and **Waiting** when unfinished steps remain but none is running. A completed root alone does not make the chain **Done**. Click a step for its individual status and logs. Recurring-chain jobs are viewed through their cron occurrence rather than duplicated in the ordinary time-ticker list.

## Path, appearance, and read-only access

Configure these inside the same `AddDashboard` callback:

```csharp
dashboard.SetBasePath("/operations/jobs");
dashboard.SetTitle("Orders — background jobs");
dashboard.SetEnvironmentName(builder.Environment.EnvironmentName);
dashboard.SetLogoUrl("/images/orders-logo.svg");
dashboard.SetTimeZone(TimeZoneInfo.Utc);
dashboard.SetReadOnly(context => !context.User.IsInRole("SchedulerAdmin"));
dashboard.SetGroupName("tickerq"); // Optional OpenAPI endpoint group.
```

`SetBasePath` changes the dashboard mount point, including its API and live-update routes. Preserve that prefix through your reverse proxy. `SetEnvironmentName` adds a visible deployment label to the dashboard and sign-in page; it does not change the scheduler namespace. `SetLogoUrl` accepts an absolute URL or browser-reachable path. `SetTimeZone` sets the dashboard display default; it does not alter the scheduler's cron interpretation. `SetReadOnly(true)` is the unconditional alternative to a per-user predicate. `SetGroupName` changes only the OpenAPI group assigned to dashboard endpoints. In host mode, the same user permissions drive the visible controls and the server write gate; see [dashboard enforcement](/docs/5.x/dashboard/authorization#what-the-dashboard-enforces).

## SignalR in multi-replica deployments

The dashboard uses SignalR messages as cache-invalidation hints. REST endpoints remain authoritative. A single application process needs no additional SignalR configuration. With multiple dashboard replicas, the default hub can reach only browsers connected to the process that sent the message, so configure a backplane when updates must appear immediately across nodes.

Install `Microsoft.AspNetCore.SignalR.StackExchangeRedis` in the host application, then configure it through the dashboard registration:

```csharp
options.AddDashboard(dashboard =>
{
    dashboard.ConfigureSignalR(signalR =>
        signalR.AddStackExchangeRedis(
            builder.Configuration.GetConnectionString("SignalRRedis")!,
            redis => redis.Configuration.ChannelPrefix =
                StackExchange.Redis.RedisChannel.Literal(
                    "tickerq:orders-production")));
});
```

This backplane is separate from TickerQ's optional Redis operational/cache provider. `options.AddStackExchangeRedis(...)` configures TickerQ storage and coordination; `dashboard.ConfigureSignalR(...)` configures dashboard message delivery. Neither implicitly enables the other.

Use a unique channel prefix when applications share Redis. Because the dashboard retains WebSocket, Server-Sent Events, and long-polling fallback, Redis deployments also need load-balancer session affinity. Azure-hosted applications can configure `AddAzureSignalR(...)` through the same hook instead. A 30-second consistency refresh repairs missed hints for active views, but it does not provide immediate cross-replica delivery.

At the reverse proxy, preserve the dashboard base path, pass WebSocket upgrade headers, disable buffering for Server-Sent Events, and set the upstream read timeout above the SignalR keep-alive interval. See [authentication and deployment](/docs/5.x/dashboard/authentication#signalr-and-reverse-proxies) and [live-update troubleshooting](/docs/5.x/guides/troubleshooting#dashboard-live-updates-are-delayed).

Set integration `DashboardUrl` to the externally reachable dashboard URL if alert messages should link back here. The URL is for message links; it does not enable dashboard hosting or authentication.
