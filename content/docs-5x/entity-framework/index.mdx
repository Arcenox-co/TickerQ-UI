title: "Entity Framework Core"
description: "Persist TickerQ jobs in your application database with provider-independent EF Core integration."
---

Use `TickerQ.EntityFrameworkCore` with one of the [supported databases](#supported-databases): SQLite, SQL Server, PostgreSQL, MySQL, MariaDB, CockroachDB, YugabyteDB, or Oracle Database. Match the TickerQ package versions to your .NET line.

## Choose the context

| Need | Registration |
| --- | --- |
| Commit business data and new jobs together | `UseApplicationDbContext<AppDbContext>(...)` and [StageAsync](/docs/5.x/entity-framework/transactional-scheduling) |
| Store jobs independently of the business context | `UseTickerQDbContext<TickerQDbContext>(...)` |

Register one operational provider. Redis can be added alongside EF for caching and node coordination; see [Redis with EF Core](/docs/5.x/redis#combine-redis-with-ef-core).

## Register your application context

This example uses SQLite. Replace `UseSqlite` with your provider's normal EF configuration when using another database.

```csharp
using Microsoft.EntityFrameworkCore;
using TickerQ.DependencyInjection;
using TickerQ.EntityFrameworkCore.Customizer;
using TickerQ.EntityFrameworkCore.DependencyInjection;

builder.Services.AddDbContext<AppDbContext>(db =>
    db.UseSqlite("Data Source=orders.db"));

builder.Services.AddTickerQ(options =>
{
    options.UseLicense("tickerq.tqlicense");
    options.UseApplicationNamespace("orders-production");
    options.UseReconciliationEpoch(1);
    options.AddOperationalStore(store =>
        store.UseApplicationDbContext<AppDbContext>(ConfigurationType.UseModelCustomizer));
});

// Define this alongside your application's entities and mappings.
public class AppDbContext(DbContextOptions<AppDbContext> options) : DbContext(options);
```

`UseModelCustomizer` adds TickerQ mappings and preserves your context's `OnModelCreating` calls. It replaces EF's `IModelCustomizer`; if your application already supplies a custom implementation, use the [manual mapping option](#map-tickerq-manually) below instead of assuming both customizers will run.

## Create the schema

Install your EF provider and design-time tooling, then generate an application-owned migration:

```sh
dotnet ef migrations add AddTickerQ --context AppDbContext
dotnet ef database update --context AppDbContext
```

Review the migration and apply it before scheduler startup. Use the same TickerQ package version and schema at design time and runtime. `EnsureCreated` is not an upgrade mechanism for an existing database.

### Supported databases

Scheduler startup verifies TickerQ's required indexes by reading the database's own catalog, so only databases TickerQ knows how to inspect can run a scheduler. Each database below passes TickerQ's relational conformance suite and an end-to-end scheduler run at the version shown.

| Database | EF Core provider | Tested version |
| --- | --- | --- |
| SQLite | `Microsoft.EntityFrameworkCore.Sqlite` | Bundled SQLite 3 |
| SQL Server | `Microsoft.EntityFrameworkCore.SqlServer` | SQL Server 2022 |
| PostgreSQL | `Npgsql.EntityFrameworkCore.PostgreSQL` | PostgreSQL 17 |
| MySQL | `MySql.EntityFrameworkCore` | MySQL 8.4 |
| MariaDB | `MySql.EntityFrameworkCore` | MariaDB 11.4 |
| CockroachDB | `Npgsql.EntityFrameworkCore.PostgreSQL` | CockroachDB 24.3 and 25.2 |
| YugabyteDB (YSQL) | `Npgsql.EntityFrameworkCore.PostgreSQL` | YugabyteDB 2024.2 |
| Oracle Database | `Oracle.EntityFrameworkCore` | Oracle Database 23ai Free |

Pomelo (`Pomelo.EntityFrameworkCore.MySql`) is also recognized for MySQL and MariaDB, but it has no EF Core 10 release, so the EF Core 10 line was tested with `MySql.EntityFrameworkCore`. Any other EF provider fails closed when a new reconciliation epoch is activated: startup throws a `TickerQStoreSchemaException` saying TickerQ cannot verify required relational indexes for that provider, and listing the supported ones.

Managed services run these same engines and use the same provider: Azure SQL Database and Azure SQL Managed Instance; Amazon RDS and Aurora for PostgreSQL and MySQL; Azure Database for PostgreSQL and MySQL; Google Cloud SQL; and hosted PostgreSQL such as Neon and Supabase. They are expected to work but were not tested separately. TickerQ relies on serializable transactions; behind a connection pooler such as PgBouncer, use session pooling or a direct connection, at least for migrations.

TickerQ retries deadlocks and serialization conflicts itself on every supported database, so an EF execution strategy such as `EnableRetryOnFailure()` is optional.

#### MySQL and MariaDB

- A MySQL schema is a database. TickerQ's default schema `ticker` therefore places its tables in a database named `ticker`. Call `SetSchema("<your database>")` to keep them in the connection's database.
- TickerQ rewrites EF Core's bulk-delete statements into a form MariaDB accepts. The rewrite is registered automatically for both `UseTickerQDbContext` and `UseApplicationDbContext`.
- To stay within InnoDB's 3,072-byte index key limit, the assistant investigation index on MySQL and MariaDB covers `(ApplicationNamespace, OccurredAt)` and is named `IX_AssistantInvestigation_Namespace_OccurredAt`.

#### CockroachDB

- Keep TickerQ's tables in the `public` schema with `SetSchema("public")`. CockroachDB cannot run EF Core's schema creation for any other schema.
- On CockroachDB 25.1 and later, add `Options=-c autocommit_before_ddl=false` to the connection string used for migrations or `AutoMigrateDatabase()`. Otherwise CockroachDB commits EF Core's migration transaction before its first schema change, and the migration fails with `Transaction is already completed`.
- `EnsureCreated()` does not create tables on CockroachDB, because its built-in `pg_extension` tables make an empty database look populated. Use migrations.

#### YugabyteDB

Connect to the YSQL API (port 5433 by default) with the PostgreSQL provider. No other configuration is required.

#### Oracle Database

- Call `SetSchema` with the Oracle user that owns TickerQ's tables, in uppercase, for example `SetSchema("TICKERQ")`. TickerQ's default schema `ticker` names a lowercase user that normally does not exist, and table creation fails with `ORA-01435: user does not exist`.
- Oracle indexes a row unless every key column is NULL, so a unique index over `(ApplicationNamespaceKey, SeedKey)` would reject a second cron without a `SeedKey`. On Oracle, TickerQ adds a virtual `SeedKeyScope` column to `CronTickers` and builds `UX_CronTickers_SeedKey` over `(SeedKeyScope, SeedKey)` instead. Migrations include it automatically.

### Current table inventory

The current EF model maps **18 tables**:

| Area | Tables |
| --- | --- |
| Schedules and history | `TimeTickers`, `CronTickers`, `CronTickerOccurrences` |
| Committed results | `TimeTickerResults`, `CronTickerOccurrenceResults` |
| Runtime coordination | `TickerQStoreMetadata`, `NodeFinalizationOutbox`, `TickerQNodes`, `TickerQControlCommands` |
| Dashboard definitions/settings | `TickerQDefinitions`, `IntegrationSettings` |
| Schedule policies | `SchedulePolicies` |
| Execution logs | `ExecutionLogs` |
| Assistant operations | `AssistantConversations`, `AssistantMessages`, `AssistantInvestigations`, `AssistantInvestigationLeases`, `AssistantInvestigationBudgets` |

All 18 mappings are present even when log persistence, AI chat history, automatic investigation, or schedule policies are not in use. Those options control runtime services and writes, not schema shape. This keeps migrations stable when a capability is enabled later. Drafts and templates share `TickerQDefinitions`; they do not create separate tables.

## Dedicated TickerQ context

If jobs do not need to share the business context, the package supplies a dedicated context. Use this **instead of** `UseApplicationDbContext`:

```csharp
using TickerQ.EntityFrameworkCore.DbContextFactory;

options.AddOperationalStore(store => store.UseTickerQDbContext<TickerQDbContext>(db =>
    db.UseSqlite("Data Source=tickerq.db")));
```

Generate migrations for that context through your application's normal design-time setup. `SetSchema(...)` selects a relational schema where the provider supports schemas; SQLite does not. `UseTickerQDbContext` also accepts the schema as an optional second argument, for example `UseTickerQDbContext<TickerQDbContext>(db => db.UseNpgsql(connectionString), schema: "jobs")`. Both set the same value, so the last call wins; omitting the argument keeps the current schema (default `ticker`). `AutoMigrateDatabase()` explicitly applies pending migrations at startup, but generating and reviewing them remains the application's responsibility. Use your deployment pipeline when schema changes need separate control.

The dedicated context supports independent manager operations. It does not make `StageAsync` join an unrelated business context; that operation requires the application-context registration.

## Map TickerQ manually

Choose `ConfigurationType.IgnoreModelCustomizer` when your application owns the complete model configuration. Add these mappings to its `OnModelCreating` method, alongside your business entities:

```csharp
using TickerQ.EntityFrameworkCore.Configurations;
using TickerQ.Utilities.Entities;

modelBuilder.ApplyConfiguration(new TimeTickerConfigurations<TimeTickerEntity>("ticker"));
modelBuilder.ApplyConfiguration(new CronTickerConfigurations<CronTickerEntity>("ticker"));
modelBuilder.ApplyConfiguration(new CronTickerOccurrenceConfigurations<CronTickerEntity>("ticker"));
modelBuilder.ApplyConfiguration(new TimeTickerResultConfigurations<TimeTickerEntity>("ticker"));
modelBuilder.ApplyConfiguration(new CronTickerOccurrenceResultConfigurations<CronTickerEntity>("ticker"));
modelBuilder.ApplyConfiguration(new NodeFinalizationOutboxConfigurations("ticker"));
modelBuilder.ApplyConfiguration(new TickerQStoreMetadataConfigurations("ticker"));
modelBuilder.ApplyConfiguration(new TickerQNodeConfigurations("ticker"));
modelBuilder.ApplyConfiguration(new TickerQControlCommandConfigurations("ticker"));
modelBuilder.ApplyConfiguration(new IntegrationSettingsConfigurations("ticker"));
modelBuilder.ApplyConfiguration(new TickerQDefinitionConfigurations("ticker"));
modelBuilder.ApplyConfiguration(new SchedulePolicyConfigurations("ticker"));

// After the TickerQ configurations: database-specific adjustments (a no-op except on Oracle,
// MySQL, and MariaDB). See "Supported databases" above.
TickerProviderModelConventions.Apply(modelBuilder, Database.ProviderName);
```

Use the same schema as `store.SetSchema(...)` (default `ticker`), and replace the ticker entity types if you extend them. Keep the complete current mapping in design-time tooling, including `ExecutionLogArchiveConfiguration`, `AssistantConversationConfigurations`, `AssistantMessageConfigurations`, `AssistantInvestigationConfigurations`, `AssistantInvestigationLeaseConfigurations`, and `AssistantInvestigationBudgetConfigurations`. Their tables remain part of the model when the related runtime feature is disabled.

`IgnoreModelCustomizer` does not disable transactional scheduling. The DI registration still installs its save/commit interceptors; the context must include the mappings above.

## Custom ticker entities

Applications can extend `TimeTickerEntity<TSelf>` and `CronTickerEntity` with their own fields. Register `AddTickerQ<MyTimeTicker, MyCronTicker>(...)` and inject managers with the same two types. Preserve the TickerQ mappings and add your fields to the application migration. Do not change ownership, status, or lease fields directly to control execution.

## Save jobs with business changes

`StageAsync` supports both time jobs and cron schedules in your application's unit of work. It is available automatically with a scoped application context; no separate enable flag or context argument is required. Read [transactional scheduling](/docs/5.x/entity-framework/transactional-scheduling).

For existing databases, replica rollout, stable cron identities, and schema ownership, use the [storage upgrade reference](/docs/5.x/guides/storage-upgrade).

## Storage options and startup

| Option | Purpose |
| --- | --- |
| `SetSchema("ticker")` | Names the relational schema, where the database supports it |
| `SetDbContextPoolSize(1024)` | Sets the dedicated TickerQ context pool size; does not resize your application's `AddDbContextPool` |
| `AutoMigrateDatabase()` | Applies existing pending migrations before scheduler initialization |
| `AddAssistantHistory(...)` | Enables EF-backed chat/proposal history, structured investigations, coordination, and retention services; the tables are already part of the model |
| `UseLegacyRuntimePartitionAdoption(namespace, epoch, legacyWritersDrained: true)` | Store-builder form of the core [legacy runtime partition adoption](/docs/5.x/guides/storage-upgrade#explicit-legacy-runtime-partition-adoption) option; it is forwarded to the core option, and a conflicting second adoption configuration is rejected |

Execution-log persistence and assistant history are optional runtime features. Their tables, integration settings, node finalization, cluster control, and saved definitions are part of the current mapping even when their dashboard surfaces are not in use. Generate and review the current model instead of copying an older fixed table list.

Concurrent scheduler startup uses stable code-defined cron identities, a unique seed index, and transactional reconciliation. TickerQ runs reconciliation through the context's execution strategy. Configure your EF provider's own transient retry policy when needed; TickerQ does not turn permanent database errors into successful startup. Replicas of the same application must also agree on their [namespace and reconciliation epoch](/docs/5.x/guides/configuration).
