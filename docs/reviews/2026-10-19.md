## Library concerns requiring separate changes

### Assistant history identity and isolation

Browser fallback history uses one `tickerq-assistant-chat` localStorage key per origin, independent of dashboard path or authenticated user. Switching accounts in a shared browser can reveal the earlier local conversation. Server history prefers `auth.username`; API-key/custom authentication uses shared names, and unnamed host authentication falls back to `host-user`. EF history filters by `UserId` but has no application-namespace partition.

The assistant, existing-user, and authorization guides now explain these boundaries. Before presenting history as isolated per user/application, the library should partition browser history by authenticated identity and dashboard, resolve server identity from a stable subject plus partition, and migrate existing history with explicit ownership handling.

Source: `src/TickerQ.Dashboard/wwwroot/src/pages/AssistantChat.tsx`, `src/TickerQ.Dashboard/Assistant/AssistantEndpoints.cs`, authentication scheme implementations, and `src/TickerQ.EntityFrameworkCore/Infrastructure/EfAssistantHistoryStore.cs`.

### Optional OpenTelemetry enqueue counter

`OpenTelemetryInstrumentation.LogJobEnqueued` overrides the base method without invoking the base counter increment. An isolated `MeterListener` probe observed zero enqueue measurements through the optional instrumentation and one through `LoggerInstrumentation`. Core `EnableActivitySource()` retains the base behavior. The telemetry guide documents this limitation; the optional package needs a source fix and regression test.

Source: `src/TickerQ.Instrumentation.OpenTelemetry/OpenTelemetryInstrumentation.cs` and `src/TickerQ.Utilities/Instrumentation/BaseLoggerInstrumentation.cs`.

## Important supported behavior now documented

- Scheduler `MaxConcurrency` limits admitted scheduler work items. Parallel chain children can execute within one item; per-function limits remain separate.
- Priority orders an acquired batch rather than providing a global priority queue.
- Ordinary time-child default run conditions and deletion policy differ from recurring-chain template defaults.
- Restarting stale work has its own policy and budget; pending cancellation does not run cancellation branches.
- EF and Redis both register log archive persistence; the last registration selects its backend even when job entities stay in EF.
- Code-defined cron retirement requires a later reconciliation after its grace period; time passing alone is not a retirement timer.
- Integration event delivery is best effort. Persisted monitoring transition state does not turn ordinary event alerts into a durable outbox.
- Monitoring observes individual function executions and daily deadlines; calendar-aware deadlines and aggregate workflow completion are not advertised.
- Dashboard authorization supports entry policies, read-only predicates, and integration-management grants; no built-in per-function/per-tenant permission matrix is claimed.
